# Qwen 0.26.5 auxiliary memory requests

Observed on Linux x64 on 2026-11-02, using npm Qwen Code 0.26.5, OAR's
unchanged adapter and a private HOME/project. A local OpenAI-compatible SSE
server returns synthetic replies and known usage. No real account is used.

The extra request is made after the main model reply and before the native
`result`, not by `dispose()`. Looking only at requests collected after
disposal initially obscured this ordering. The memory request has its own
system instructions and a final user message asking for memory extraction;
the earlier user messages contain the conversation history.

| Scenario | Main / memory requests | Observation |
| --- | --- | --- |
| Empty session, then dispose | 0 / 0 | No model request. |
| Two ordinary turns, then dispose | 2 / 2 | One memory request per turn, both before disposal begins. |
| Resume, no new input, then dispose | 0 / 0 | Loading history alone did not trigger extraction. |
| Resume and run one new turn | 1 / 1 | Extraction includes the restored and new conversation. |
| Delay memory reply by 1.5 seconds | 1 / 1 | Turn completion waits for the response, then idle disposal returns. |
| Delay memory reply by 8 seconds | 1 / 1 | Still completes before native result and disposal; this is turn time, not shutdown grace. |
| Dispose while memory reply is streaming | 1 / 1 | Connection closes before the terminal chunk and usage; no native result. |

Repeating disposal on the same OAR session adds no request in any scenario.
The delayed-response controls send an initial SSE text chunk immediately,
then delay the terminal chunk and usage. The interrupted control starts
disposal only after the server observes the memory request. Server `finish`
and `close` timestamps distinguish a completed response from a closed stream;
they do not claim a provider's real billing behavior.

## Usage

Each main response reports **101 input / 7 output** tokens; each completed
memory response reports **201 input / 11 output**. A fresh turn's native
result and OAR total are **302 / 18**, and two turns produce **604 / 36**.
After resuming that conversation for another turn, the native cumulative
result is **906 / 54**. OAR preserves it in the record stream but keeps the
resumed session's public total null, as documented in
[Qwen usage](../../docs/runtimes/qwen.md#usage-and-failures).

Disposal during the unfinished memory response produces an `exited` reply,
without a native result or complete OAR turn usage. The raw assistant frame
still carries the main response's **101 / 7**; that partial number excludes
the unfinished memory work. No product behavior changes in this experiment.

## Reproduction and scope

```sh
OAR_QWEN_BIN=/absolute/path/to/qwen-0.26.5 pnpm tsx \
  experiments/qwen-native/dispose-memory.ts oar-trial-run/qwen-memory
```

The [probe](dispose-memory.ts) writes `raw.json` (request bodies and OAR
records) and `selected.json` (timing, marker presence, usage and exit facts).
The committed [selected observations](memory-2026-11-02.json) retain all
seven controls. Delays are controlled inputs, not performance promises.
The server returns one text reply, without memory tool calls; these controls
do not establish all possible extraction policies, tool sequences or behavior
on macOS/Windows.

The [resume-prompt vendor regression](../../sea-trial/vendor/resume-fresh-prompts.vendor.test.ts)
selects the main request by its last user message and checks a new request was
observed. This keeps memory requests' independent system instructions out of
the comparison while preserving every raw request in failure artifacts.
