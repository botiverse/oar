# OpenCode v2 startup: WAL recovery and fresh databases

OpenCode 2.3.0 still needs OAR's startup gate for concurrent schema creation
([upstream #53879](https://github.com/anomalyco/opencode/issues/53879)).
On Linux x64, 9/24 native ACP first starts on fresh databases failed with
`table account_state already exists`; all 24 passed with OAR's gate.
The full adapter also opened and disposed all 24 sessions. The separate
v1 warm-WAL failure in [#64590](https://github.com/anomalyco/opencode/issues/64590)
did not reproduce on v2, whose SQLite driver protects its first WAL pragma.

Measured November 18, 2026, with Node 24.19.0 and the unmodified official
Linux x64 OpenCode 2.3.0 executable. Its bytes match the integrity-verified
`@opencode/cli-linux-x64@2.3.0` archive. All configurations and databases were
synthetic and isolated; there were no logins, prompts or provider requests.
[Selected results](v2-results.json) retain the observations and raw-report
fingerprints. Full protocol, stderr, strace and database files remain local.

## Warm-WAL controls and driver ordering

The [original probe](README.md#reproduce) leaves 64 MiB of committed WAL
pages over a schema initialized by the same native executable. Each control
uses six concurrent pairs, with three successful serial preparations excluded
from the counts. No failed start is retried.

| Control | Opens | Failed |
| --- | ---: | ---: |
| v1.19.5, ungated comparison | 12 | 2 |
| v2.3.0, ungated comparison | 12 | 0 |
| v2.3.0, probe-only gate through initialize | 12 | 0 |
| v2.3.0, ungated under strace | 12 | 0 |

Both v1 failures report `database is locked` before initialize. In the traced
v2 run, every pair encountered recovery-lock contention and still opened.
The selected excerpt in `v2-results.json` shows one process failing to take
SHM locks at offsets 120 and 122, then acquiring the write lock at offset 120
after 527 ms.
These results concern this controlled trigger, not every possible lock failure.

The v2.3.0 tag resolves to `a6b15d33daf6ab7d35569f6d711fdb630b9f04e7`.
Its high-level [database.ts:42 to 44](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/core/src/database/database.ts#L42)
still requests WAL before setting `busy_timeout`, but that is not its first
pragma. [sqlite.bun.ts:1 to 13](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/core/src/database/sqlite.bun.ts#L1)
delegates to `@effect/sql-sqlite-bun`, pinned to 4.1.0 in
[bun.lock](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/bun.lock).
In that package's [official 4.1.0 archive](https://registry.npmjs.org/@effect/sql-sqlite-bun/-/sql-sqlite-bun-4.1.0.tgz),
`package/src/SqliteClient.ts:163 to 192` defaults the timeout to five seconds,
sets it before the first WAL pragma, retries a lock timeout within that budget
with a 10 ms schedule, then restores the timeout. The installed executable
contains the same ordering. The v1 early-pragma explanation therefore does
not apply to this v2 release, and this measurement supplies no v2 reproduction
for #64590.

## Fresh-database controls

Each of six rounds creates a new isolated HOME and XDG tree, asserts the
native data directory does not yet exist, then opens four processes against
that same directory. No serial start prepares that round's database. The
three preparation starts use other directories, so this measures fresh
databases, not a cold machine or an uncached executable.

| v2.3.0 control | Opens | Failed | Failure |
| --- | ---: | ---: | --- |
| Native ACP, no gate | 24 | 9 | `table account_state already exists`, before initialize |
| Same native ACP, actual OAR startup gate | 24 | 0 | |
| Full OAR adapter, current gate | 24 | 0 | All 24 also disposed successfully |

Every ungated round had at least one failure. Native `acp` starts its own
`serve --stdio --port 0` child; the saved stderr identifies the schema
bootstrap failure before the outer readiness error. The gate only changes
launch ordering: it owns startup until initialize answers, then permits the
next process while the preceding session continues. The direct gated control
imports the actual `acquireOpenCodeStartup` helper, not the older probe-only
gate. The full adapter independently confirms the same result with its normal
launch arguments and cleanup. Disposal recorded exit 143 for 20 native roots
and exit 0 for four; all disposal calls completed without an error.

The database layer's [migration lock](https://github.com/anomalyco/opencode/blob/a6b15d33daf6ab7d35569f6d711fdb630b9f04e7/packages/core/src/database/database.ts#L50)
is an in-process semaphore keyed by file path. The driver timeout does not
serialize bootstrap across native processes. OAR therefore keeps the v2 gate
for #53879. Remove that gate only after an upstream fixed release passes these
fresh-database concurrent controls without serialization. A warm-WAL pass or
issue closure alone does not meet that condition. The v1 removal condition
remains the separate [warm-WAL control](README.md#adapter-boundary-and-removal).

## Reproduce

Use a new output directory for each invocation, outside any ancestor OpenCode
configuration. Node 24+, Python 3 with sqlite3 and the exact native executable
are required. `strace` is additionally required for the traced control.

```sh
OAR_LOCK_LOG_LEVEL=debug pnpm tsx experiments/opencode-database-lock/probe.ts /absolute/opencode-v2 /tmp/oar-v2-wal 6 eof recovery,guarded
OAR_LOCK_LOG_LEVEL=debug OAR_LOCK_STRACE=1 pnpm tsx experiments/opencode-database-lock/probe.ts /absolute/opencode-v2 /tmp/oar-v2-wal-traced 6 eof recovery
pnpm tsx experiments/opencode-database-lock/probe.ts /absolute/opencode-v1 /tmp/oar-v1-wal 6 eof recovery
OAR_LOCK_LOG_LEVEL=debug pnpm tsx experiments/opencode-database-lock/probe.ts /absolute/opencode-v2 /tmp/oar-v2-cold 6 eof cold,cold-gated
OAR_LOCK_LOG_LEVEL=debug pnpm tsx experiments/opencode-database-lock/probe.ts /absolute/opencode-v2 /tmp/oar-v2-cold-adapter 6 eof cold-adapter
```

The v1 recovery and ungated v2 fresh-database commands can exit 1 as their
measured failure. They retain every outcome. Direct native RPCs have the
existing 20-second bound; the full adapter keeps its normal initialization
budget. The v2 log-level spelling is lowercase `debug`; v1 uses `DEBUG`.
An initial invocation with uppercase `DEBUG` on v2 failed all three CLI
preparations and produced no WAL samples. It is recorded separately and
excluded from the measurements above. A separate one-round smoke check after
probe cleanup reproduced 2/4 fresh-database failures without the gate and 0/4
with it; those samples are not pooled with the six-round comparison.
