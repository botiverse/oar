## Codex 0.164.0: resume preserves the saved tier

The first native vendor run passed 45 tests and failed the service-tier
test: after a priority turn, an omitted resume option now reads back
`priority`, whereas the test expected `default`. This is a native policy
change. The public OAR contract already leaves an omitted tier to the
runtime, and OAR's readback agreed with the actual provider requests.

A six-turn comparison using real 0.163.0 and 0.164.0 executables against
the same local provider recorded:

| Step | 0.163.0 readback | 0.164.0 readback |
| --- | --- | --- |
| New thread, explicit `priority` | `priority` | `priority` |
| Resume, tier omitted | `default` | `priority` |
| Resume, explicit `flex` | `flex` | `flex` |
| Set config to `priority`, resume with tier omitted | `priority` | `flex` |
| New thread with the same config, tier omitted | `priority` | `priority` |
| Resume original thread, explicit `default` | `default` | `default` |

Every provider request matched the readback: `priority` and `flex` appear
verbatim in `service_tier`; `default` omits that field. Explicit effort
`high` still takes effect with the flex resume. This agrees with the
[upstream resume-settings change](https://github.com/openai/codex/pull/55923)
included in [0.164.0](https://github.com/openai/codex/releases/tag/rust-v0.164.0).

The [vendor test](../../sea-trial/vendor/service-tier.vendor.test.ts) now
expects saved tiers on omitted resumes and includes a separate new-thread
control for the current configuration. It checks all six provider requests;
explicit `default`, rejected `fast` alias and unknown-tier checks remain.
The corrected test passed, covering the one failure from the first run.
All 16 applicable shared behavior cases also passed. No adapter code changed.

## Cold MCP resume remains broken

The [direct ACP probe](../opencode-mcp-resume-native.ts) imports no OAR code.
On 2.1.4 its initial session called echo, but only **one of six cold
resumes** did so: resumes one through five omitted the call; six succeeded.
All seven native connection logs reported the echo server with one tool.

The saved transcript contains three catalog updates: initial addition,
removal 47 ms after the first resume's prompt, and re-addition 2,337 ms
after the sixth resume's prompt. There is no separate removal/addition
pair for every intermediate resume in this run. The removal persisted
across those turns. The [six successes on October 21](2026-10-21.md#opencode-212)
had already retained a removal/re-addition window; they were not evidence
of a fix. [OAR #371](https://github.com/botiverse/oar/issues/371) and
[upstream #54794](https://github.com/anomalyco/opencode/issues/54794) remain open.
OAR adds no retry, sleep or alternate catalog.

## Resumed system prompts

A later Linux x64 check on `bea5d7c` used explicitly selected Claude
2.1.309 and Codex 0.164.0 executables, temporary homes and the local scripted
provider. Each case created a session with an old marker, ran one turn,
disposed the process, and resumed the native session with a new marker.
Captured model requests, rather than option echoes, showed:

| Runtime | Option changed on resume | Actual next model request |
| --- | --- | --- |
| Claude 2.1.309 | `systemPrompt` | Old marker retained; new marker absent |
| Claude 2.1.309 | `appendSystemPrompt` | Old marker retained; new marker absent |
| Codex 0.164.0 | `systemPrompt` | New marker applied; old marker absent |
| Codex 0.164.0 | `appendSystemPrompt` | Old marker retained; new marker absent |

The first attempt inadvertently selected the default Claude 2.1.292 and
Codex 0.162.0 installations. Those logs were retained separately; the table
uses only reruns with the verified current binaries. No account or paid
provider was used.

The new [vendor regression](../../sea-trial/vendor/resume-system-prompt.vendor.test.ts)
originally expected each new marker and failed all three ignored-option
cases before the adapter fix. OAR now refuses those explicit resume options
before any child starts; an omitted option still resumes with saved
instructions. The regression captures the provider request after that
omission and continues to check that Codex replacement applies. A separate
[unit regression](../../tests/resume-system-prompt.test.ts) asserts no process
is spawned on refusal, including empty and repeated values. This is a
breaking change for hosts that repeat the same options on every open.
