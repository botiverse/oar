## Kimi 2.4.0

All 15 shared cases passed, with four existing capability skips. The first
vendor run passed ten cases but the hook fixture exceeded its shortened
2,000 ms initialization deadline. Both unchanged hook cases passed in the
focused control. The complete vendor suite then passed all 11 cases with
CI's two-worker setting. This does not establish why the first start timed
out. OAR's 30-second Kimi request default is unchanged.

The four local OAuth/login regressions passed using the explicit
`OAR_KIMI_LOGIN_COMMAND` selector: browser permission/suppression, native
storage, status, logout, timeout and cancellation remain covered. An initial
invocation used the session selector instead of the login selector and ran
the machine's older executable; its two failures are not attributed to 2.4.0.

This change updates the Linux/macOS ACP, three-platform login and Windows
ACP observation pins to 2.4.0, along with the login fixture's version.
The product's previously verified minimum of 2.3.3 stays unchanged. Linux
results are established here; macOS/Windows login and macOS ACP results
must come from this PR's CI. The Windows ACP workflow needs a manual run on
this branch before merging the pin update, since it otherwise runs only
after main pushes. The independent Windows observation is not silently
promoted to a general PR gate.

## Qwen 0.26.3 and 0.26.4

Version 0.26.4 appeared during this inspection. Both versions passed all
11 native vendor tests and 16 shared cases, with three capability skips.
The direct `reply-blocks` scenario still reports the thinking snapshot
with the initial message id, then the text snapshot with a different id
without another `message_start`. The structural Qwen-only snapshot rule
from PR #528 therefore remains necessary; no adapter change is made here.

The extension-store lock limitation also persists. In 0.26.4, initialize
returned after **1,888 ms** with the lock held and no provider request. The
first prompt stayed blocked until release, then completed. An ordinary
later prompt completed while the lock was held. The 0.26.3 control returned
initialize after 1,731 ms and showed the same sequence. Initialization
success still does not establish first-prompt readiness or safe concurrent
launches in a shared HOME.

The installed presets in 0.26.4's `chunk-HHIU5CDK.js` retain fourteen
literal provider `envKey` names. Those and the four native protocol key
names are covered by the credential reader's 18 `KEY_NAMES`; configured
custom provider `envKey` values remain read dynamically. Attribution maps
and generic third-party SDK fields are not additional native preset
credential sources. No new key source or credential-reader regression was
needed. This was a source audit and local-provider test, not another run
against Bugen's private Token Plan key.

Upstream has added automated source analyses to
[extension-store locking #15796](https://github.com/QwenLM/qwen-code/issues/15796#issuecomment-6469876861)
and [snapshot identity #15875](https://github.com/QwenLM/qwen-code/issues/15875#issuecomment-6500361969).
They explain the respective initialize/readiness and thinking-finalization
paths. Neither reply is an executed upstream reproduction or a released
fix; both behaviors still reproduce in 0.26.4. On a native snapshot fix,
recheck the structure regressions and remove the Qwen-only rule if it is
no longer needed.

## OpenCode 2.2.1

### Native startup

Three shared-suite runs each lost at least one native process before
readiness. The results were respectively **13 pass / 4 skip / 2 fail**,
**14 pass / 4 skip / 1 fail**, and **15 pass / 3 skip / 1 fail**. In the last
run, a case failed during startup before reaching its capability skip.
Native stderr first reported a standalone server exiting before readiness;
enabling the nested server's logs then exposed
`SQLiteError: table account_state already exists`.

The new [startup probe](../opencode-startup.ts) starts the same native
`serve --stdio --port 0` child used by ACP, without OAR, an account, a
session or a model request. Each batch has an isolated HOME/XDG state. It
compares two sequential starts, four simultaneous starts sharing a fresh
database, and four simultaneous starts sharing the sequential control's
already initialized database. It records readiness, exit, timings and
private stderr, then closes the owned process groups.

| Binary | Sequential | Concurrent fresh database | Concurrent existing database |
| --- | --- | --- | --- |
| 2.2.1 initial | 2/2 ready, 361-406 ms | 3/4 ready; one exits 1 after 426 ms with `account_state already exists` | 4/4 ready, 374-465 ms |
| 2.2.1 final probe | 2/2 ready, 326-396 ms | 1/4 ready; three exit 1 after 353-360 ms with the same schema error | 4/4 ready, 348-401 ms |
| 2.2.0 control | 2/2 ready, 402-420 ms | 4/4 ready, 438-529 ms | 4/4 ready, 361-388 ms |

The [selected startup observations](2026-10-29-opencode-startup.json)
contain no native state or account identifiers. The final probe run added
version/platform metadata and isolated the version query; its startup
sequence was unchanged. The 2.2.0 shared-suite
control also passed 15 cases with four skips. One passing old-version batch
does not prove a new regression or old-version immunity: the
[October 27 check](2026-10-27.md#opencode-220) already retained a different
SQLite-lock startup failure.

At upstream tag commit `3ebcf9a32c7b28f658cfee80775448929361727a`,
[`database.ts`](https://github.com/anomalyco/opencode/blob/3ebcf9a32c7b28f658cfee80775448929361727a/packages/core/src/database/database.ts)
keeps its bootstrap semaphore in a module-local map keyed by filename.
[`migration.ts`](https://github.com/anomalyco/opencode/blob/3ebcf9a32c7b28f658cfee80775448929361727a/packages/core/src/database/migration.ts)
checks `sqlite_master` before entering the bootstrap transaction and then
creates the full schema. Separate processes do not share that semaphore.
Together with the direct failure, this supports a concurrent cold-bootstrap
race [src/env]. It does not identify the cause of every earlier exit or
prove that warmup fixes all startup failures. No OAR lock, retry, warmup or
forced sequential test execution was introduced. Hosts may serialize the
first startup until readiness before opening further sessions over that
data directory. The [upstream issue draft](../opencode-startup-report.md)
retains these controls and is awaiting maintainer review/publication.

### Existing boundaries and MCP

The v2-specific boundary probe passed eight of ten checks: unsupported
prompt options, queued input, child attribution, ordinary history resume,
abort, disposal and raw steer refusal with the original turn completing.
Ordinary resume retained the session id and recalled its marker; six native
child frames formed a nested child graph. Two checks failed:

- The model catalog initially failed with `Location plugins did not finish
  activating`. Separate fresh-state and warm-state catalog controls each
  returned eight models. The initial failure remains unexplained.
- A new session called the MCP echo tool, but its cold resume completed
  without the tool call. The independent native ACP reproduction, with no
  OAR imports, then called echo on only **two of six cold resumes**. All six
  prompts returned `end_turn`; that result alone does not prove MCP success.

The second resume removed the echo tool from its catalog 32 ms after prompt
start. It was not added back until 17,819 ms later, during the fifth resume.
The sixth resume removed it again without a later addition before that run
ended. These notices span prompts; they are not six separate observed
remove/re-add pairs. The [upstream cold-resume issue](https://github.com/anomalyco/opencode/issues/54794)
remains open. The separate live `tools/list_changed` control passed:
alpha was replaced by beta, with only the expected handlers called.

An early invocation of the v1 vendor suite against v2 produced five passes
and five failures. That suite assumes v1 tool names, prompt replacement and
tool declarations; it is not a valid v2 compatibility gate. Its output is
retained locally, and the v2-specific probes above provide the relevant
results. They do not amount to a fully passing v2 upgrade.

## Repeating the checks

Use `OAR_KIMI_BIN`, `OAR_QWEN_BIN`, `OAR_OPENCODE_BIN` and
`OAR_ANTIGRAVITY_BIN` to select the installed copies. Run the corresponding
shared and vendor suites; Kimi login uses `OAR_TEST=kimi-login` and
`OAR_KIMI_LOGIN_COMMAND`. Antigravity's shared harness is
`pnpm tsx experiments/acp-aimock-behavior.ts antigravity`.

For native startup, run `pnpm tsx experiments/opencode-startup.ts
/absolute/path/to/opencode <new-output-directory>`. A failed native start
is a recorded observation, not a script assertion. Other reusable probes:
`qwen-native/probe.ts` (`reply-blocks`), `qwen-native/lock-lifetime.ts`,
`antigravity-native-settings.ts`, `antigravity-steering.ts`,
`opencode-release-lines.ts`, `opencode-mcp-resume-native.ts`, and
`mcp-tools-catalog-changed.ts opencode`. OpenCode's boundary/MCP scripts use
the external free model; the startup script makes no model request.
Local raw evidence is retained under `artifacts/runtime-2026-10-29-*`.
