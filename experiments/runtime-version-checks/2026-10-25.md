## Kimi 2.3.2

All 11 native tests and 15 applicable shared behavior cases passed. Coverage
includes MCP attachment and list changes, additional-directory handling,
opening hooks, native failure classification and cold resume. The hook test
kept its shortened 2,000 ms request limit; the earlier test-specific timeout
did not recur. OAR's product default remains 30 seconds for ordinary requests.

The [release notes](https://github.com/MoonshotAI/kimi-code/releases/tag/%40moonshot-ai/kimi-code%402.3.2)
change default delegation guidance and restrict swarms to explicit swarm mode,
which is unavailable through ACP. These are upstream policy changes; the
scripted provider does not establish how a real model follows that guidance.
OAR's existing ACP mapping needed no change.

## Qwen 0.26.1

The npm release identifies source
[`b475278`](https://github.com/QwenLM/qwen-code/tree/b475278c4a300acebe6cfc990a9e1b1d18819bfc).
All six native vendor tests passed, including cumulative fresh-session usage,
unknown resumed usage totals, provider catalog and effort readback,
stdio/HTTP MCP delivery, prompt options, tool denial, missing-session refusal
and the explicit extension-lock failure. All 16 applicable shared behavior
cases passed with the existing two-worker CI limit and per-session HOMEs;
resume reused its original HOME and cwd.

The independent cold-start sample completed initialize in 1,604 ms and its
first turn in a further 3,728 ms. It used a separate HOME from the suite and
did not prewarm those sessions. One successful Linux sample does not establish
a startup bound or resolve earlier macOS/Windows load failures.

The [direct native probe](../qwen-native/README.md) ran `plain`, `tools`,
`permission` and `catalog` against fresh and resumed sessions. Initialize
reported medium effort applied without an override. Ordinary turns completed;
interrupt produced `result/error_during_execution`, and the following prompt
completed. Both MCP scenarios called echo before and after resume. Default
permission mode issued one `can_use_tool` request in the fresh session and
none on resume. The configured catalog returned
the local model; environment-only configuration returned no model entries.

The vendor credential test passed on the main checkout. Separately, the
post-exit audit from pending [PR #481](https://github.com/botiverse/oar/pull/481),
head `05ca88a`, was run with this new binary. After the resumed process exited,
it scanned all persisted files in the isolated HOME and found neither
synthetic MCP credential. That one focused check also passed; the pending
fixture change was not folded into this documentation update.

### Initialize still precedes extension readiness

After a completed warmup and clean disposal, the
[lock-lifetime probe](../qwen-native/lock-lifetime.ts) held the extension-store
lock externally. Initialize returned in **1,755 ms** with no provider request.
The first prompt remained blocked during the next 300 ms, then completed
after release. An ordinary later prompt completed while the lock was held.
The separate vendor case that keeps the lock held exhausted native retries
and reported `Extension store is busy` as `failed/unknown`, without a provider
request. These observations preserve the existing limitation: waiting only
for initialize, or completing a previous warmup, does not prove readiness.
The later-prompt control is not a guarantee about extension refresh operations.

### Standalone installation

OAR's real `install()` ran the official installer in a Linux bubblewrap
sandbox with an empty HOME, read-only host filesystem and no Qwen on PATH.
It installed 0.26.1, and `installation()` found the executable in the isolated
default install directory without adding it to PATH. A sentinel `.bashrc`
was unchanged; a second install returned `already_installed`. This verifies
Linux installation and discovery, not standalone session behavior or
macOS/Windows installation. Session checks above used the npm executable.
