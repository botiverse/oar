## Cursor 1.1.0

### Inclusive input accounting

The installed SDK's `dist/esm/index.js`, module `src/agent/usage-types.ts`,
changed both `toTokenUsage` and `sumTokenUsage`. The equivalent formulas are:

```text
1.0.40: totalTokens = inputTokens + outputTokens + cacheReadTokens + cacheWriteTokens
1.1.0:  totalTokens = inputTokens + outputTokens
```

Both functions still retain the cache-read and cache-write fields. OAR does
not use the SDK's `totalTokens`; its old projection added both cache fields
to `inputTokens`. With the exact SDK 1.1.0 dependency, that would count cache
parts twice. The projection now copies `inputTokens` and retains both cache
parts independently. The optional peer, development dependencies, CLI
runtime dependency, lockfile and release-age exclusions move together to
1.1.0. There is no version branch or promise to support the previous SDK.
Hosts using Cursor must install that exact SDK when upgrading OAR.

Three root turn updates and their matching `run.wait()` usage are retained
in the [native fixture](../../tests/fixtures/cursor-usage-1.1.0.json), with
conversation content and identifiers omitted:

| Turn | Input | Output | Cache read | Cache write | Native total |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 8,476 | 19 | 0 | 0 | 8,495 |
| 2 | 8,539 | 6 | 7,680 | 0 | 8,545 |
| 3 | 8,589 | 6 | 7,680 | 0 | 8,595 |

These confirm nonzero cache reads are already included. All real samples
reported zero cache writes: **nonzero cache-write inclusion was not verified
with a real provider**. Its mapping follows the SDK source and has a separate,
explicitly synthetic nonzero-write regression. The native fixture regression
checks accumulated input, output, cache parts and optional reasoning against
the matching run totals. No old-version compatibility assertion is retained.

This is a visible behavior correction: Cursor `input` can become smaller
because cached input is no longer counted twice. The [attribution contract](../../docs/spec/attribution.md#cache-reads-and-writes)
and runtime page now identify the 1.1.0 source and today's evidence.

### Session, tools and local authentication

All 12 applicable [live scenarios](../live-contract.ts) passed on the first
run with `gpt-5.4-nano`; `kill-runtime` remains skipped for the in-process SDK.
The initial [tool-denial probe](../cursor-disallowed-tools.ts) passed its
baseline and restricted new session, then failed the required-read assertion
on resume: the model quoted the previously read file from history without
calling read again. No denied shell/MCP call or handler execution occurred.
The probe now creates a new file for each phase immediately before prompting.
With the original assertions and deadlines, all three phases passed: baseline
shell and MCP executed, while restricted new/resumed sessions still used read
and never executed the denied tools.

The [login/logout probe](../cursor-login/README.md) passed its network guard
and all 11 scenarios. The [configuration-source probe](../cursor-user-configuration/README.md)
passed all four controls: default/exclusion ignored user configuration,
native explicit user sources loaded it, and the synthetic stored login was
used without being rewritten. These use local substitutes, not real login or
inference. SDK declarations remain compatible with OAR's existing calls;
new optional filesystem and resource-provider surfaces are not exposed by
this change.

All live attempts, including the first failed tool probe, comprise 21 runs.
Nineteen report usage; two cancelled runs omit it. Reported totals are
**338,939 input + 3,845 output = 342,784 tokens**, with **231,424 cache-read**
tokens already inside input, zero cache writes, and 2,012 reasoning tokens
inside output. These are native SDK reports, not independent billing or
proof of child-agent charge coverage; the two omissions prevent a complete
usage total. No further paid request was made to seek nonzero cache writes.

## OpenCode 2.2.0

The first shared suite had 14 passes, four skips and one failure in
`session.observer-isolation`: the standalone native server exited before
readiness. Its saved native log identifies `SQLiteError: database is locked`.
An unchanged recheck passed all 15 applicable cases with four skips. Elapsed
times were 15.023 and 15.854 seconds respectively; stderr and native state
were retained before cleanup. This repeats the documented 2.1.4 startup
observation, not evidence that every past startup failure has that cause.

The catalog returned nine models. `systemPrompt` and `appendSystemPrompt`
were both refused as expected on v2. The MCP list-change probe passed warm
discovery, alpha-to-beta replacement, beta execution and removal of alpha
without invoking its former handler.

The [independent cold-resume probe](../opencode-mcp-resume-native.ts) completed
its fresh echo call and all six resumed calls on free Big Pickle. Every
resume still produced a removal/re-addition window:

| Cold resume | Prompt to tool removal (ms) | Prompt to re-addition (ms) | Echo called |
| --- | ---: | ---: | --- |
| 1 | 160 | 3,184 | yes |
| 2 | 80 | 1,260 | yes |
| 3 | 39 | 1,344 | yes |
| 4 | 41 | 1,271 | yes |
| 5 | 48 | 1,608 | yes |

The catalog race therefore remains. Six successful calls do not supersede
the five failed cold calls on 2.1.4 or establish an upstream fix. Wire

The [v2.2.0 release page](https://github.com/anomalyco/opencode/releases/tag/v2.2.0)
provides no detailed changes that establish a fix for this race.

## Qoder 1.1.79

The first shared suite had 16 passes, two skips and one failure in
`session.cursor-replays-without-loss-or-duplication`. Native stderr reported
`/tmp/qoder-settings-1cc73090ab49cfc6.json: Unexpected end of JSON input`
before the control response. The unchanged recheck passed 17 cases with two
skips.

The installed native bundle writes inline `--settings` using a shared
`qoder-settings-<content-hash>.json` path in the system temporary directory.
The hash of the fixture's JSON exactly matches the failed path. This is
Qoder's inline-settings file, not OAR's private MCP or prompt files. The
source path and failure are consistent with an interrupted read during an
overwrite, but the exact interleaving was not captured. Twelve serial and
12 concurrent inline opens all passed without reproducing it. Twelve
concurrent controls using separate settings files also passed.

The test fixture now writes an immutable settings file inside its own HOME
and passes its path. All eight native tests, 17 shared cases (two skipped)
and eight native priority controls passed with that fixture. OAR continues
to forward a host's `launchArgs` unchanged; a host using inline settings can
still select the shared native path. The new
[comparison probe](../qoder-native/inline-settings.ts) submits no model prompt
or login, retains every outcome, and can be rerun independently.

The [upstream report draft](../qoder-native/inline-settings-report.md) is for
a human to submit through Qoder's official Bug Reports forum. No upstream
post was sent. It explicitly states that the failure was intermittent and
not reproduced in the comparison batches, and suggests unique paths or
atomic replacement. The [release notes](https://docs.qoder.com/release-notes/qoder-cli)
mention hooks, additional-directory rule loading, PNG errors and shell
termination; this check does not independently verify every listed change.
No paid Qoder request was made, and earlier real-account quota limits remain.

## Repeating the checks

Use the checked version in an isolated installation and select its executable
with `OAR_CLAUDE_BIN`, `OAR_KIMI_BIN`, `OAR_OPENCODE_BIN` or `OAR_QODER_BIN`.
Native suites use `OAR_TEST=claude-aimock`, `kimi-aimock` or `qoder-native`;
shared ACP cases use `experiments/acp-aimock-behavior.ts kimi|opencode`.
Run the linked login, configuration, priority, inline-settings, tool-catalog
and cold-resume probes separately. Cursor's live scenarios and tool-denial
probe use a real account and quota; the login and configuration substitutes
do not. Local raw evidence is retained under `artifacts/runtime-2026-10-27-*`.
