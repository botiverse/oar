### Known startup boundary

The existing [cold-start probe](../opencode-cold-start.ts) opens two independent
ACP processes concurrently against one fresh database, then repeats in another
HOME after serial initialization. On 2.2.6, one cold open succeeded and one
exited 1 before readiness; both prepared opens succeeded. The failed open's
retained stderr is `Standalone server exited before reporting readiness`.
There is no SQLite diagnostic in this sample, so it does not establish whether
this was `account_state already exists`, `database is locked` or another cause.
No model requests were made.

This is a recheck of the [known startup limitation](../../docs/runtimes/opencode.md#startup-and-compatibility),
not a newly discovered 2.2.6 regression. [Upstream #53879](https://github.com/anomalyco/opencode/issues/53879)
remains open with no update since October 29. OAR adds no retry or lock.

### Known v1 vendor boundary

Selecting 2.2.6 for the entire `opencode-aimock` vendor suite produces eleven
passing and five failing cases. The five failures are the already documented
[v1-only vendor boundary](../../docs/runtimes/opencode.md#verification-and-open-gaps):
three scripts call direct names such as `echo_echo` or `host_echo`, one reads
MCP declarations from the provider's `tools` array, and one expects v1 prompt
replacement. v2 uses Code Mode for MCP and OAR refuses its prompt replacement.

The captured model results explicitly report that those direct tool names are
unavailable. The list-change control does receive another native `tools/list`,
but its v1 model-view parser returns null. Running the same five cases on
2.2.5 reproduces every failure. These results are not v2 compatibility passes
and do not invalidate the actual Code Mode calls in today's separate MCP probe.
The fixtures and their assertions are unchanged; the CI pin change applies
only to the dedicated v2 isolated-cleanup case. Experimental sharing keeps
its separate 2.2.5 pin and remains outside production admission.

## Repeating the checks

Select exact isolated binaries through `OAR_ANTIGRAVITY_BIN`,
`OAR_OPENCODE_BIN` and `OAR_QODER_BIN`, with `CI=1`,
`OAR_TEST_REQUIRE_AVAILABLE=1` and `OAR_TEST_CONCURRENCY=2`:

```sh
pnpm tsx experiments/runtime-versions.ts
pnpm tsx sea-trial/all.ts antigravity-aimock
OAR_TEST=antigravity-aimock pnpm vitest run sea-trial/vendor --maxWorkers 2
pnpm tsx sea-trial/all.ts opencode-aimock
OAR_TEST=opencode-cleanup pnpm vitest run sea-trial/vendor/opencode-cleanup.vendor.test.ts
pnpm tsx experiments/opencode-cold-start.ts /tmp/opencode-cold-start-results
pnpm tsx sea-trial/all.ts qoder-native
OAR_TEST=qoder-native pnpm vitest run sea-trial/vendor --maxWorkers 2
pnpm vitest run tests/login/qoder-login.test.ts
pnpm tsx experiments/qoder-native/replay-catalog.ts /absolute/qodercli 1.1.85
```

The [boundary probe](../opencode-release-lines.ts) takes binary, isolated cwd
and output paths followed by `catalog appendSystemPrompt systemPrompt` for
the three no-inference checks. It uses the invoking process's environment,
so supply an empty HOME/XDG configuration. The cold-start and Qoder commands
retain their failures and return nonzero when their assertions fail. For the
v1-fixture comparison, run `mcp-servers-acp`, `serve-mcp-tools` and
`mcp-tools-list-changed` vendor files with `OAR_TEST=opencode-aimock`, once per
2.2.5 and 2.2.6 executable. That comparison is diagnostic, not a v2 gate.
