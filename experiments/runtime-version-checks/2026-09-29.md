## What was observed

All five runtimes completed the basic prompt, retained native frames with
dense sequence numbers, reported the effective model, and completed a shell
tool round with matching start/end call IDs and the requested final marker.
The four CLI runs cover only these two scenarios; they do not revalidate
all control, subagent or failure behavior.

Pi also passed multi-turn, busy/late control, steer, queue, abort, mid-turn
dispose, cursor replay, resume and bad-model scenarios. Steer landed in the
same turn; the queued input ran as a spontaneous next turn; abort and
mid-turn dispose produced the runtime's aborted outcome. Resume kept the
same native session ID, recalled the marker and restarted the stream at
sequence zero. Subagents and process killing were skipped because this
adapter has no native subagents and runs in-process.

Kimi exposed the shell lifecycle and final text but no command on the
projected tool start; its tool end contained a terminal reference instead
of inline output. Its total token usage remained unknown while context
occupancy was reported. Grok emitted SDK diagnostics about responses to
`skills-reload`; the two scenarios still completed. These observations
are retained rather than treating a passing scenario as complete fidelity.

Kimi 2.1.1 was installed separately and selected with `OAR_KIMI_BIN`; the
host's default executable was still 0.38.0. Pi's version was read from the
SDK that OAR resolves, not from a host command named `pi`. Pi used the host's
configured exe.dev LLM integration through its native provider extension.

## Repeat the check

```sh
pnpm tsx experiments/runtime-versions.ts > versions.json
pnpm tsx experiments/live-contract.ts pi --model <available-provider/model> --out <evidence-dir>/pi
pnpm tsx experiments/live-contract.ts codex --model <available-model> --only basic,tool-detail --out <evidence-dir>/codex
```

Set `OAR_KIMI_BIN` (or the corresponding runtime override) when probing an
isolated install. Select a model from `oar models <runtime>` for the current
host. Compare the version inventory with the most recent probe report:
probe changed versions, preserve `report.json` and voyage logs, and record
failures before changing the adapter. Matching versions alone prove no
runtime behavior. No-change daily checks need neither a dependency bump
nor an OAR release.
