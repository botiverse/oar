## Cursor 1.4.0

The **SDK cannot currently be supplied to OAR's typed `CursorSdk` loader**.
Its common `Run.steer` return type now includes
`{ outcome: "queued"; run?: Run }`. OAR's interface admits only
`"complete_delivered" | "revert_to_followup"`, so assigning the SDK module
to `CursorSdk` fails with TS2322. The root compiler check reports 15 affected
sites with 1.4.0; the same source passes after restoring 1.3.1.

The [minimal reproduction](cursor-sdk-check.ts) independently compiles one
host assignment against a supplied SDK directory, without executing that
SDK or changing dependencies. With 1.3.1 it exits zero; with 1.4.0 it exits
two and identifies the new union member. It uses `skipLibCheck` only to
isolate the host assignment from dependencies' internal declarations.

```sh
npm install --prefix /tmp/oar-cursor-140 --no-audit --no-fund @cursor/sdk@1.4.0
node_modules/.bin/tsx experiments/runtime-version-checks/cursor-sdk-check.ts /tmp/oar-cursor-140/node_modules/@cursor/sdk
node_modules/.bin/tsx experiments/runtime-version-checks/cursor-sdk-check.ts node_modules/@cursor/sdk
```

The installed ESM bundle places the new queued result in its **cloud** run
implementation (`dist/esm/448.js`). The local implementation in
`dist/esm/993.js`, and its wrapper in `index.js`, still return the two
strings. These are source observations, not a native cloud steering test.
OAR creates local agents, but the SDK's shared type still prevents a typed
upgrade. Simply treating the queued object as a refusal would also give
incorrect ownership if that result were ever admitted: the SDK says the
server already owns the follow-up. Adaptation needs its own review.

- 160 existing Cursor unit tests passed with the SDK selected. These use

variables. Those and the four native authentication variables all appear
