## Qwen 0.26.5

All eleven OAR native vendor tests and 16 applicable behavior cases passed.
The independent `plain`, `catalog` and `reply-blocks` scenarios recorded
successful ordinary prompts before and after resume, the expected error
result for an interrupted prompt, and completion of a subsequent prompt.
These recordings do not by themselves assert semantic isolation after abort.

The published 0.26.1 through 0.26.5 bundles contain two distinct mechanisms.
`normalizeModelToolCallIds` renames ids already present in session history
to `<id>__qwen_dup_N`, drops repeated ids in the same response, and generates
`call_qwen_N` when an id is missing. Separately,
`isReplayOfHandledToolCall` compares the original provider id, tool name and
arguments with handled calls. A repeated id with different arguments can
execute under its renamed id; an identical replay is not executed and gets
an error tool result. Qwen's recorded tool-call ids can therefore differ
from the model's raw ids. A compatible endpoint that reuses ids such as
`call_0` can also cause a legitimate later repeat, such as reading the same
file again, to be suppressed.

The direct MCP probe initially failed in both `tools` and `permission`:
it reused `native-echo` with the same tool and arguments after resume.
Qwen renamed it to `native-echo__qwen_dup_2`, then emitted an error tool
result stating that the duplicate had not been executed again. The local
provider did not match the renamed result and returned 404. Both resumed
turn results were `error_during_execution`, despite the old observation
script exiting 0. These initial failures remain separate evidence, not passes.

The retained October 25 **0.26.1** recordings were also rechecked. Both
scenarios show a successful fresh echo, then the same renamed error tool
result on resume. Their final resumed turn results nevertheless say
`success` with `is_error: false`. Thus the earlier report's claim that echo
was called before and after resume was incorrect: the second invocation
was suppressed, even though the turn completed. Corrections beside the
[original report](2026-10-25.md#qwen-0261) and
[probe summary](../qwen-native/README.md) preserve the historical text.
The selected JSON retains each tool result separately from the final turn
result, with hashes of the original recordings and audited bundles.

The probe now supplies distinct fresh/resumed ids and echo markers, then
asserts successful native MCP results and both actual echo bodies received
by the provider. Only the two affected scenarios were repeated after this
fixture correction. Both passed for new and resumed sessions:

| Scenario | Fresh MCP | Resumed MCP | Permission requests, fresh / resumed |
| --- | --- | --- | --- |
| tools | `echo:fresh-probe` | `echo:resumed-probe` | 0 / 0 |
| permission | `echo:fresh-probe` | `echo:resumed-probe` | 1 / 1 |

This corrects the independent probe, not Qwen's duplicate-id handling or
OAR's transport. The OAR vendor fixtures already use distinct tool-call ids.
Separate native vendor coverage will check normalization, replay errors and
same-response duplicates through OAR's records.

Two existing native limitations still reproduce:

- A reply has one `message_start`, then thinking and text blocks each at
  index 0. The thinking snapshot matches the initial id, while the text
  snapshot has a different id without a new `message_start`. OAR's
  structural snapshot matching remains necessary.
- With a warm HOME and the extension-store lock held, initialize returned
  in 1,859 ms without a provider request. The first prompt remained blocked
  during the 300 ms observation and completed after lock release. An
  ordinary later prompt completed while the lock was held again. This does
  not prove that later extension operations never acquire the lock.

The published bundle's fourteen provider-preset credential variable names
are all covered by OAR's local credential reader; none was added to OAR.
[Qwen issue 15796](https://github.com/QwenLM/qwen-code/issues/15796) and
[issue 15875](https://github.com/QwenLM/qwen-code/issues/15875) remain open,
with unchanged comments. Automated analysis is not evidence of a released fix.

`OAR_CODEBUDDY_BIN` and `OAR_QWEN_BIN` to their absolute executable paths,
then run:

```sh
OAR_TEST_REQUIRE_AVAILABLE=1 pnpm tsx sea-trial/all.ts codebuddy-aimock qwen-aimock
OAR_TEST=codebuddy-aimock pnpm vitest run sea-trial/vendor --maxWorkers 2

```

[`codebuddy-consecutive-prompts.mjs`](../codebuddy-native/2026-10-29/codebuddy-consecutive-prompts.mjs)

## Repository validation

The first full check passed 2,947 tests and failed one existing
`deliver-interrupt.test.ts` case: after two rejected empty inputs, a valid
interrupt returned `rejected` instead of `prompted`. Neither that test nor
product code differs from the base commit. The original assertion did not
retain the rejection branch. An unchanged focused rerun passed all twenty
cases; twenty repetitions with full-result diagnostics in the full suite
also passed. These passes do not explain the original failure.

A controlled timing comparison exposes a fragile fixture assumption:
normal cancellation shared the forced-exit tests' 50 ms fallback. Pausing
the host event loop for 100 ms after the native cancel was sent produced
`runtime_exited` in all three 50 ms controls; each returned the original
input id as undelivered and sent no replacement prompt. With a 5 s
fallback, all three paused controls prompted successfully. The three
unpaused controls at each timeout also passed. This establishes the
fallback mechanism, not the cause of the first uninstrumented failure.

A separate test-only follow-up retains the full delivery result and record
tail, gives ordinary cancellation a suitable fixture budget, and makes the
forced-exit/input-return branch an explicit controlled-timing regression.
No product change is justified by these observations.

`CI=1 pnpm run check` subsequently passed: type checking, lint, 2,948
tests and all eighteen applicable mock behavior cases. The original
interrupt test and all product files were unchanged for this final run.
`actionlint` passed for the changed CI workflow. Cross-platform CI for this
change remains a merge requirement; it is not implied by the Linux
observations above.
