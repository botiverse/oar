## Cursor 1.2.0

### Existing interface compatibility

All 12 applicable [live scenarios](../live-contract.ts) passed with
`gpt-5.4-nano`; `kill-runtime` remains skipped for the in-process SDK. All
three [tool-denial controls](../cursor-disallowed-tools.ts) passed, using a
new file per phase: baseline shell/MCP execution, restricted creation and
restricted resume with read still usable. The local
[login/logout probe](../cursor-login/README.md) passed its network guard and
all 11 scenarios. No real login flow was repeated.

**The required peer remains 1.1.0.** SDK 1.2.0 was validated against existing
interfaces using a temporary installation; the dependency manifests,
lockfile and release-age exceptions retain 1.1.0. No current OAR feature or
fix needs the new SDK, so this check does not require another host upgrade.
Adoption will accompany a feature or fix that needs it. No adapter behavior
or version branch was added, and the new manual summary control is not exposed.

The installed declarations add `Agent.summarize()` and `SDKSummaryMessage`.
The bundle's `run.stream()` path converts native summary start/completion
into `summary` messages with `running`, `completed` or `error` status and an
optional fallback flag [src]. The `onDelta` accumulator still filters
`summary`, `summary-started` and `summary-completed`. OAR currently consumes
`onDelta` and `run.wait()`, so these compaction statuses are not yet in its
record stream. Reading both channels without losing or duplicating existing
updates is a separate follow-up using the existing compaction event types;
manual `summarize()` control remains outside this change.

### Input and cache accounting

SDK 1.2.0's `src/agent/usage-types.ts` module in the installed
`dist/esm/index.js` retains the 1.1.0 formulas:
`totalTokens = inputTokens + outputTokens` in both `toTokenUsage` and
`sumTokenUsage` [src]. Cache fields remain separate parts of input. OAR's
projection therefore needs no change.

Three real root turn updates and their matching `run.wait()` usage are kept
in the [1.2.0 fixture](../../tests/fixtures/cursor-usage-1.2.0.json), without
conversation text or identifiers:

| Turn | Input | Output | Cache read | Cache write | Native total |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 | 8,467 | 18 | 0 | 0 | 8,485 |
| 2 | 8,529 | 6 | 7,680 | 0 | 8,535 |
| 3 | 8,579 | 6 | 7,680 | 0 | 8,585 |

The projection regression now runs against both the 1.1.0 and 1.2.0 native
fixtures, asserting accumulated fields and `input + output == totalTokens`.
Nonzero cache reads and reasoning are observed. Nonzero cache writes remain
unverified with a real provider; that mapping is supported by SDK source and
the separate synthetic regression. These checks do not establish the
meaning of the native input field in 1.0.40.

### Configuration observer

The first configuration-source run passed default exclusion, then failed to
observe the positive control's user skill read. An unchanged second run
failed the same way; a third diagnostic run retained observed paths and
also failed. Each native log reported one loaded user skill and rule.

The 1.2.0 text decoder in `dist/esm/336.js` uses `fs.promises.open`, then
`FileHandle.stat` and `FileHandle.readFile`. The 1.1.0 decoder used
`fs.promises.readFile`, which was the only read path the probe observed.
The probe now observes actual `FileHandle.readFile` calls too, preserving
the original handle, return values and errors. Opening a path alone does
not count as reading it.

All four original controls then passed: default/exclusion ignored user
configuration, explicit native user sources loaded it, and the stored
synthetic login was used without rewriting its file. Assertions and
deadlines are unchanged. All four controls also passed again after restoring
the required SDK 1.1.0. No external service or inference was used.
[Probe](../cursor-user-configuration/README.md).

### SDK 1.0.40 to 1.1.0 resume

The new [cross-version probe](../cursor-upgrade-resume.ts) uses separate
processes to avoid loading both bundles into one host. SDK 1.0.40 created an
agent with `gpt-5.4-nano`, completed a text-only turn remembering a random
marker, and disposed. SDK 1.1.0 then opened the same agent and working
directory through OAR, omitting `model`. Its native run lookup retained the
first run and its model; OAR reported the same agent id and model. A second
prompt, containing no marker, recalled the exact marker. Both native runs
finished and remained listed [env]. Tools and user configuration were disabled
for this small check. The two runs reported **6,920 tokens** in total.

Source comparison of the installed 1.0.40 and 1.1.0 bundles also found
identical `agents`/`runs` SQL and identical checkpoint `blobs`/`meta` SQL
[src]. Both checkpoint stores set `PRAGMA user_version = 1`. The separate
agent-index schema does not explicitly set `user_version`; these are not
claims about every database's pragma. The same schema statements are present
in 1.2.0. The real upgrade test was specifically **1.0.40 to 1.1.0**, not a
rollback test or a general promise for every older agent.

### Real-account usage

The cross-version probe, live suite and tool controls comprise 20 native
runs. Eighteen report usage; two cancelled runs omit it. Reported totals are
**282,035 input + 2,802 output = 284,837 tokens**, including **196,352
cache-read** tokens within input, zero cache writes and 1,453 reasoning
tokens within output. The two omitted usage values prevent a complete
billing total. These are SDK reports, not independent billing verification
or proof that child charges are complete. No further paid request was made
to seek nonzero cache writes.
