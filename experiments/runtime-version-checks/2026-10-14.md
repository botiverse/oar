## Antigravity 1.4.0

The [official registry](https://github.com/agentclientprotocol/registry/blob/main/antigravity-acp/agent.json)
points to [Google's distribution](https://dl.google.com/agy-extensions/releases/linux/agy-acp-server-1.4.0-linux-x86_64.zip),
containing `agy_acp_server.par` and `localharness_external`. Both were
installed together; Linux still needs `--uid=`. The distributed ACP source
and direct native requests established these changes:

- `initialize` advertises `systemPrompt.append`. The new/load/resume metadata
  field is `_meta.antigravity.systemPrompt.append`. New and resumed provider
  requests contained the supplied append alongside the built-in harness;
  a resume omitting it no longer put either prior append in system instructions.
- `configOptions` groups thinking variants into model families and exposes
  `thinking_level` in category `thought_level`. The existing shared ACP
  effort path already sets and reads this selector. Native low/high choices
  reached the provider. An omitted resume choice selected high after low.
- The fresh API-key session listed five model families, with a low/medium/high
  menu only for its current `gemini-3.8-flash` model. Other models' menus can
  differ; OAuth and gateway catalogs were not tested with accounts.
- Both harmless MCP env and header sentinels still appeared in the native
  conversation database and WAL after disposal, mode `0600`. OAR's
  `mcpServerCredentials` refusal remains in force.

OAR now carries `appendSystemPrompt` through the advertised channel and
uses the current `_meta.antigravity` namespace for tool denials too.
Unadvertised append support is refused before session creation.
Non-empty tool denials also require the advertised `antigravity` namespace
and otherwise fail before creation or resume. A real 1.3.0 negative probe
confirmed why: sending the new namespace left `run_command` and `view_file`
in the provider's tools, while the old `agy` control removed both. There is
no old-version fallback in OAR. On 1.4.0 both namespace probes removed the
tools, while the baseline still offered them. The fake-agent regression covers rejection
on both creation and resume when initialize lacks the capability.
`listModels` attaches the native effort menu and default only to the current
model; it does not fabricate menus for the other entries. System-prompt
replacement remains refused.

**Host-visible changes:** upgrade the Antigravity server and its companion
harness together to 1.4.0; the adapter now uses that release's metadata
namespace. `appendSystemPrompt` is no longer an always-refused Antigravity
option. With the new native runtime, model picker ids and
`Session.model()` are family selectors such as `gemini-3.8-flash`, while
`Session.effort()` reports the separate level. Use returned catalog ids;
do not reconstruct a selector from a model suffix. Only the current entry
carries the observed effort menu. On resume, resend the append and effort
when they should apply again.

The existing eight native vendor tests passed on 1.4.0: MCP attachment and
credential refusal, built-in tool denial and resume, image-only prompts,
and provider failure evidence. The added settings test also passed,
including native refusal of an invalid effort. Tool-denial tests passed
again after changing the metadata namespace. Pure tests pin the sanitized
native catalog and open/resume mappings. The new reproducible probe is
[`antigravity-native-settings.ts`](../antigravity-native-settings.ts); it
uses a temporary home, fake credentials and a scripted provider, then
removes its files. It deliberately uses direct ACP for the credential test
because OAR correctly refuses those entries.
[`antigravity-tool-filter-meta.ts`](../antigravity-tool-filter-meta.ts)
reproduces the namespace comparison with the same isolation; it only
inspects provider tool declarations and does not execute any tool.

The new native `/usage` command remains message text, and account-plan
`tier` metadata is not a per-session service tier. No `usage_update` arrived
in these scripted turns. This cycle does not establish new token/context
accounting, child attribution, account login, Windows/macOS behavior, or
append persistence through native compaction.

## OpenCode v2 2.0.29

The [release](https://github.com/anomalyco/opencode/releases/tag/v2.0.29)
and [comparison with 2.0.28](https://github.com/anomalyco/opencode/compare/v2.0.28...v2.0.29)

plugin rejection handling. The comparison changes no ACP source file.

[`opencode-release-lines.ts`](../opencode-release-lines.ts) passed all ten
boundary probes in a new HOME/XDG configuration: catalog (12 ids), both
instruction refusals, concurrent input, child sessions, resume, session MCP
on new/resume, abort, disposal and forced steering. The last probe retains
the native boundary: explicit steer is accepted but the original reply wins.

The MCP round succeeded in this run. That does not close the intermittent
resume catalog race, [OAR #371](https://github.com/botiverse/oar/issues/371) /
[upstream #54794](https://github.com/anomalyco/opencode/issues/54794).
The upstream report remains open with the previously observed independent
reproduction and proposed refresh work; no new fix was available to verify.
No duplicate upstream report was sent.

## Reproduce

The new Antigravity settings probe and native vendor suite use
`OAR_ANTIGRAVITY_BIN` pointing to the isolated server with its companion
harness beside it. Existing entry points remain:

```sh
pnpm tsx experiments/runtime-versions.ts
OAR_TEST=claude-aimock pnpm vitest run sea-trial/vendor
OAR_TEST=claude-aimock pnpm sea-trial
OAR_TEST=antigravity-aimock pnpm vitest run sea-trial/vendor
pnpm tsx experiments/antigravity-native-settings.ts
CI=1 pnpm run check
pnpm run build
```

Use the corresponding executable overrides when rerunning. The OpenCode
boundary command and its isolation options are documented in its script.
Antigravity native vendor tests run locally; the existing CI matrix does
not install that large distribution.
