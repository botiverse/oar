## Antigravity 1.4.3

The server and companion `localharness_external` came from the same official
Linux x64 archive linked by the [ACP registry entry](https://github.com/agentclientprotocol/registry/blob/main/antigravity-acp/agent.json).
Its SHA-256 matched the registry:
`0634ce5306ba92c932945455e7a83fda78e2d99c33fa8aa6ee0566206a382714`.

### MCP tool titles changed

The first native vendor run passed eight tests and failed one strict
expectation in `mcp-servers-acp.vendor.test.ts`. The tool calls and completed
turns were present, but the runtime now names an MCP call `<server>_<tool>`
instead of `Running <tool>`. The same unchanged test passed against the
paired 1.4.1 distribution in another temporary home. Recorded native frames
show the difference directly:

| Field on the opening ACP `tool_call` | 1.4.1 control | 1.4.3 |
| --- | --- | --- |
| Stdio echo title | `Running echo` | `echo_echo` |
| HTTP echo title | `Running echo` | `remote_echo` |
| Resumed stdio echo title | `Running echo` | `echo_echo` |
| `rawInput` for the stdio call | `{ "text": "stdio-call" }` | `{ "arguments": { "text": "stdio-call" }, "text": "stdio-call" }` |
| `_meta` | Absent | `mcp: { server: "echo", tool: "echo" }`, `is_mcp_tool_call: true` |

OAR already projects the opening native title as `tool_call_started.tool`
and retains the full native frame. Its text input remained `stdio-call`.
No adapter change was necessary. The test now expects the two distinct
server-prefixed titles, preserving the exact sequence, provider echo and
credential checks. All nine native tests then passed on 1.4.3. All 15
applicable shared behavior cases passed on their first run.

### Settings, persistence and tool-list changes

The [native settings probe](../antigravity-native-settings.ts) still sees
appended instructions on creation and resume; omitting the append on resume
removes it. Explicit low and high thinking levels reach the provider.
Omitting the level after low reads back high. The picker still groups five
model families with a separate thinking selector.

Harmless MCP environment and header sentinels remain in both the conversation
database and WAL after native process disposal. Repeating the probe with two
inherited umasks gave:

| Inherited umask | Native home mode | Database / WAL mode | Both sentinels persisted |
| --- | --- | --- | --- |
| `0022` | `0755` | `0644` / `0644` | Yes |
| `0077` | `0700` | `0600` / `0600` | Yes |

The home sits inside the probe's private temporary parent. These are observed
modes, not a runtime-enforced `0600` guarantee. OAR's refusal of MCP entries
carrying environment or header credentials remains necessary and unchanged.
No real credential was supplied to this persistence probe.

The [catalog probe](../mcp-tools-catalog-changed.ts) called alpha, replaced it
with beta, and then attempted removed alpha. The next model request's current
MCP catalog contained beta only. Beta ran; the removed alpha attempt invoked
no handler. This retains the `mcpToolsListChanged: "full"` evidence.

## Claude 2.1.310

All 53 native tests and 17 applicable shared behavior cases passed on their
first run. Coverage includes tool search/list changes, MCP attachment and
resume, denial, streamed input, child attribution, structured output, tiers,
effort, directories, error redaction, opening hooks and OAR's explicit resume
prompt refusals. Those refusal tests check OAR's behavior; they do not bypass
the adapter to establish whether 2.1.310 changed native resume prompt handling.

The reserved-name probe still found all five refused server names absent
from native initialization and tool discovery. The ordinary control name
connected and exposed its tool. ToolSearch still removes withdrawn tools
from search while retaining a previously loaded schema; calls to a removed
tool fail.

The Linux login-browser probe passed all three controls against synthetic
OAuth. The default opener ran once; `openBrowser: false` opened no browser;
the failing opener ran once without falling back to a default browser.
Login and the subsequent status query completed in each case. This adds
Linux evidence only. Earlier Windows/macOS coverage and the macOS login
completion limit remain in the [probe README](../claude-login-browser/README.md).

The [upstream changelog](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md#21310)
includes gateway retry, monitor availability, compaction and Windows hook
fixes. These scripted Linux checks do not independently verify every release
note or Windows behavior.

## Reproduction and validation

Use an isolated home/configuration and explicit binary paths. Keep the
Antigravity companion harness beside its server. Existing tests and probes
provide all the checks:

```sh
OAR_TEST=antigravity-aimock pnpm vitest run sea-trial/vendor --maxWorkers=2
OAR_TEST=claude-aimock pnpm vitest run sea-trial/vendor --maxWorkers=2
OAR_TEST=grok-aimock pnpm vitest run sea-trial/vendor --maxWorkers=2
OAR_TEST=claude-aimock pnpm sea-trial
pnpm tsx experiments/acp-aimock-behavior.ts antigravity
pnpm tsx experiments/acp-aimock-behavior.ts grok
pnpm tsx experiments/antigravity-native-settings.ts
pnpm tsx experiments/mcp-tools-catalog-changed.ts antigravity
pnpm tsx experiments/grok-prompt-options.ts
pnpm tsx experiments/claude-reserved-mcp-names.ts
pnpm tsx experiments/claude-login-browser/probe.ts /path/to/claude 2.1.310
```

Set `OAR_ANTIGRAVITY_BIN`, `OAR_CLAUDE_BIN` and `OAR_GROK_BIN` to the
executables under test. The old Antigravity comparison used the pre-change
MCP test with only `mcp-servers-acp.vendor.test.ts` selected. The original
failure was preserved before updating its expected titles; no assertion or
timeout was weakened. Repository-wide check and build results are recorded
with the pull request after the final edits.
