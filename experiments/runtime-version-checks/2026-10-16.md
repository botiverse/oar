## Pi 1.3.0: resume must use this open's tools

The [upstream release](https://github.com/earendil-works/pi/releases/tag/v1.3.0)
restores the active tool selection from a saved transcript. This exposed a
real OAR regression: after a session excluded `bash` and an MCP tool,
resuming with an omitted or empty `disallowedTools` kept those tools disabled.
Two existing native denial tests failed before the fix; their assertions
and timeouts were not changed.

OAR now restores the current native default tools and default-active
extension tools immediately after native session creation, before
`session_start` callbacks. Pi still applies the current `excludeTools` and
exposure rules. A resumed session has the same tools as a fresh session
with the same options. This does not enable every registered builtin or
an extension that declares `defaultActive: false`.

The regression compares fresh and resumed provider tool lists with custom
`defaultTools`, default-active and inactive extensions, a codemode-only
extension, MCP tools, and a `session_start` callback that changes the list.
Both omitted and empty denylists restore defaults; a current denylist still
applies. The original forced-denied-call test also passes.

The independent `pi-upgrade-resume.ts` probe created a session under 1.2.0
and resumed it in a fresh 1.3.0 process. Native id and saved model were
preserved, earlier user/assistant messages reached the new provider request,
and the new OAR record stream began at sequence zero.

The dependency floors for Pi coding-agent and Pi AI become `^1.3.0`.
Pi Durable and Chord optional peers become `~1.3.0`; hosts using the Durable
entry must upgrade their native packages together. Clean installation of
packed OAR/CLI packages and the browser demo passed with these peers.

One upstream migration matters independently of OAR: the Kimi Coding
provider now uses OpenAI chat completions and
`https://api.kimi.com/coding/v1`. Hosts with a custom `models.json` override
must include `/v1` in that endpoint. No real Kimi provider request was made
here, and other new upstream provider features are not claimed as tested.

## Native command exits: numbers, and a Durable observation limit

The real CodingTools implementations were exercised with `exit 0`,
`exit 7`, `kill -TERM $$`, and a non-command `read` control. No manually
constructed signal result was used as evidence.

| Native path | Reported field | Observed exits | OAR result |
| --- | --- | --- | --- |
| Pi CodingTools | `result.structuredContent.exit_code` | 0, 7, 143 | Same numeric `tool_call_ended.exitCode` |
| Durable nested `api.executeTool` call | `result.structuredOutput.exitCode` in `tool_execution_end` | 0, 7, 143 | Same numeric `exitCode`, with the companion Durable fix |
| Durable model-issued tool call | The event carries `entry`, without structured output | No structured exit field | `exitCode` absent, including a failing command |
| Non-command `read` | No structured exit field | Absent | `exitCode` absent |

Both local execution environments encode signals as `128 + signal number`.
SIGTERM is 143, not null. #414 corrects the ordinary Pi projection, test and
contract wording. The [companion Durable fix](https://github.com/botiverse/oar/pull/415) reads
only the native nested result. It never parses the model output or diagnostic text for a
code. It preserves an explicit native null if one is supplied; that unit
boundary is not a claim that the built-in local environment emits null.

The Durable event shape is visible in the native
[watch projection](https://github.com/earendil-works/pi/blob/v1.3.0/packages/durable/src/harness/events.ts)
and [nested result](https://github.com/earendil-works/pi/blob/v1.3.0/packages/durable/src/harness/tool.ts).
The new real-runtime tests check native fields and OAR events together,
then JSON-serialize and parse the records. The Durable fix also passed its
native test on 1.2.0, so it can merge independently of the dependency upgrade.

## OpenCode: distinguish the two lines and retain failed attempts

The [v1.19.2 release](https://github.com/anomalyco/opencode/releases/tag/v1.19.2)
changes release-line update/install handling. OAR's v1 catalog, prompt
configuration and native MCP checks passed. The first shared behavior run
failed at the installation probe: `opencode --version` exceeded the existing
15-second limit while the cases were opening concurrently. Independent fresh
processes returned the version in 0.96 and 1.00 seconds. An unchanged retry
of the same concurrent behavior probe passed all applicable cases. The first
failure is retained; its cause is not established, and neither a runtime
fix nor a larger timeout is claimed.

The [v2.0.30 release](https://github.com/anomalyco/opencode/releases/tag/v2.0.30)
was checked separately. Both lines list 12 models in the isolated scripted
configuration. v2 still refuses `systemPrompt` and `appendSystemPrompt`.

Running the v1-oriented `opencode-aimock` vendor selection against v2
produced 5 passes and 5 failures. The failed cases require direct MCP tools
in the provider's `tools` array, a model-view classification from that array,
or v1's prompt replacement. Those are not v2's protocol. No assertion was
weakened, and this run is not reported as a passing v2 vendor suite.

The separate `mcp-tools-catalog-changed.ts` probe handles v2's Code Mode
catalog. It warms up discovery, confirms `alpha`, replaces it with `beta`,
calls `beta`, then deliberately calls removed `alpha`. v2 relists the MCP
server, adds `beta` in a system update and explicitly withdraws `alpha`.
Only the first `alpha` and the later `beta` reach the host handlers; the
removed call fails locally. Historical mentions of `alpha` remain in the
request, so a whole-request substring search would give a false result.
This supports the existing `full` declaration without mistaking title
requests or old history for the current catalog.

[Upstream #54794](https://github.com/anomalyco/opencode/issues/54794) remains
open with the same October 12 independent reproduction and investigation;
no fix was posted to verify. Today's aimock MCP-resume tests do not reproduce
or disprove the separately recorded cold-resume race with a real model.
[OAR #371](https://github.com/botiverse/oar/issues/371) stays open, and no
duplicate upstream report was sent.

## Reproduce and validation limits

Use isolated executables selected through `OAR_CLAUDE_BIN`, `OAR_CODEX_BIN`,
`OAR_GROK_BIN` and `OAR_OPENCODE_BIN`. Keep account credentials out of the
process environment and use a fresh home for executable probes. Run the
OpenCode vendor command with v1; select v2 for the catalog experiment.

```sh
pnpm tsx experiments/runtime-versions.ts
OAR_TEST=claude-aimock pnpm vitest run sea-trial/vendor
OAR_TEST=codex-aimock pnpm vitest run sea-trial/vendor
OAR_TEST=pi-aimock pnpm vitest run sea-trial/vendor
OAR_TEST=pi-durable-aimock pnpm vitest run sea-trial/vendor
OAR_TEST=grok-aimock pnpm vitest run sea-trial/vendor
OAR_TEST=opencode-aimock pnpm vitest run sea-trial/vendor
pnpm tsx sea-trial/all.ts
pnpm tsx experiments/acp-aimock-behavior.ts grok
pnpm tsx experiments/acp-aimock-behavior.ts opencode
pnpm tsx experiments/claude-reserved-mcp-names.ts
pnpm tsx experiments/grok-prompt-options.ts
pnpm tsx experiments/opencode-prompt-options.ts
pnpm tsx experiments/opencode-release-lines.ts
pnpm tsx experiments/mcp-tools-catalog-changed.ts opencode
pnpm tsx experiments/pi-upgrade-resume.ts /path/to/older-oar-checkout
CI=1 pnpm run check
pnpm run build
pnpm run clean-install
pnpm run durable-demo:smoke
```

The combined fixes passed the full local gate: typecheck, lint, 1,819 unit
tests and all applicable mock behavior cases. Package builds, clean packed
installation and the Chromium browser smoke test passed. The two independent
PRs also run their own commit gates before submission.

Native validation here is Linux-only. POSIX signal cases are skipped on
Windows; zero/nonzero exit and non-command controls remain enabled. This
report does not establish new Windows/macOS behavior, real-account login
behavior, every upstream feature, or a fix for the known OpenCode resume race.
