# Cursor SDK per-call context

The required SDK 1.4.1 exposes `model-call-completed` with one model call's
input count. OAR previously retained that update without projecting it.
The last call's `usage.inputTokens` can supply current model-input context;
it must not be replaced with the sum reported at turn end.

This November 18 inspection uses the installed 1.4.1 SDK and retained native
records from the previously authorized November 17 acceptance. It made no
new account, model or token-count requests. New controls use native SDK schemas
and a scripted SDK session offline.

## Evidence

[Selected fields](selected.json) retain only the per-call and turn usage
objects cited here, plus their original record sequence and agent depth.
The original task 278 voyages remain local. Counts are not inferred from
message length or cumulative totals.

| Recorded scenario | First call input | Last call input | Last call cache read | Turn input |
| --- | ---: | ---: | ---: | ---: |
| Tool call followed by final answer | 13,465 | 13,595 | 12,800 | 27,060 |
| Resume scenario, first observed turn | 13,456 | 13,456 | 12,800 | 13,456 |
| Resume scenario, second observed turn | 13,542 | 13,542 | 12,800 | 13,542 |

In the tool case, `13,465 + 13,595 = 27,060`. The context reading is 13,595;
adding the 12,800 cache-read subset again would overstate it. Native cache
writes in these samples are zero. Output and reasoning counts remain spend
information, not extra input context. Each cited event belongs to the root.

The [published SDK 1.4.1](https://www.npmjs.com/package/@cursor/sdk/v/1.4.1)
provides these primary source surfaces:

- `dist/esm/vendor/cursor-sdk-shared/delta-types.d.ts`,
  `ModelCallCompletedUpdateSchema`: explicitly describes one call's whole
  prompt, including cache reads and writes, separately from a turn's total.
- `dist/esm/144.js`, converter case `modelCallCompleted`: forwards the native
  `modelCallId` and input, output, cache and reasoning counts to the public
  `model-call-completed` update.
- The public `ModelCallCompletedUpdateSchema` validates this shape;
  `NestedTaskUpdateSchema` excludes it. The converter's nested-task filter
  also excludes it, so no child-context support is claimed.
- `step-started` and `step-completed` carry identity/timing, not token counts.
  `run.d.ts` marks `run.wait().usage` and `run.usage` cumulative.
  `messages.d.ts` marks stream `usage` per-turn; `usage-types.d.ts` describes
  `agent.getUsage()` as billed totals and grouped runs/turns.

## Projection and limits

A valid nonnegative finite native `inputTokens` updates
`usage.context = { tokens: inputTokens, contextWindow: null, percent: null }`.
It does not add a spend event or change the turn-total accumulator. No window
is borrowed from a catalog. Missing input adds no context event and explicit
zero stays zero.

This is the last observed model-input count, not a reconstruction of later
local messages or the output generated by that call. Each open starts unknown,
including resume. A completed summary resets the reading to unknown; a later
observed model-call update restores it. The summary and delta streams have no
shared native sequence, so this conservative invalidation can remain unknown
if a summary completion is delivered after the newer call's update. OAR does
not reorder the two views using inferred timing.

The SDK producer and retained frames establish the field's native meaning.
Offline controls validate the published schema, replay the two-call sample
through OAR, retain 27,060 spend while exposing 13,595 context, reject missing
or malformed input, preserve explicit zero, and clear/restore context across
compaction. No new live platform or account acceptance is claimed.
