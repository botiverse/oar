# ACP CI baseline: 2026-10-29

Kimi, Grok and OpenCode v1 now have dedicated Linux, macOS and Windows
jobs. Each runs the unchanged shared behavior cases and existing native
vendor tests against local scripted providers. No account login, real
model request or product adapter change is needed.

## Reproducible entry and installation

The [workflow](../.github/workflows/ci.yml) pins these npm distributions,
matching the [latest completed daily inspection](runtime-version-checks/2026-10-28.md):

| Backend | Exact install | Native command |
|---|---|---|
| `kimi-aimock` | `@moonshot-ai/kimi-code@2.3.3` | `kimi acp` |
| `grok-aimock` | `@xai-official/grok@1.0.70` | `grok agent stdio` |
| `opencode-aimock` | `opencode-ai@1.19.5` | `opencode acp` |

For each backend, run:

```sh
OAR_TEST=kimi-aimock OAR_TEST_REQUIRE_AVAILABLE=1 OAR_TEST_CONCURRENCY=2 pnpm sea-trial
OAR_TEST=kimi-aimock pnpm vitest run sea-trial/vendor --maxWorkers 2
```

Use `OAR_KIMI_BIN`, `OAR_GROK_BIN` or `OAR_OPENCODE_BIN` to pin an installed
executable. The shared suite's ACP composition is the same helper used by
`experiments/acp-aimock-behavior.ts`; it does not introduce another adapter.
A missing installation exits 1 when `OAR_TEST_REQUIRE_AVAILABLE=1`.
Regression tests launch the real suite entry with deliberately missing
paths for all three backends, plus a local optional-installation control
that still exits 0. Startup exceptions also fail rather than skip.

The npm manifests publish Windows x64, macOS arm64/x64 and Linux x64
support for these versions. Kimi is the Node distribution already exercised
by the three-platform native login CI; Grok and OpenCode carry platform
binaries as optional npm dependencies. Their package metadata can be
rechecked with `npm view <exact-package> optionalDependencies scripts os cpu`.
The jobs cache npm downloads by OS, architecture and exact package; they
still install and print the native version on every run. Runtime HOME and
mutable global installations are not cached.

## Measured Linux baseline

xxwork, Linux x64, Node 24; the three backends ran concurrently, with each
backend's shared suite followed by its vendor suite, using the CI setting of
two concurrent shared cases and two Vitest workers. Durations below are
whole commands including pnpm startup, not isolated performance benchmarks.

| Backend | Shared pass / skip / fail | Shared seconds | Vendor pass | Vendor seconds |
|---|---|---:|---:|---:|
| Kimi 2.3.3 | 15 / 4 / 0 | 54.89 | 11 | 103.77 |
| Grok 1.0.70 | 17 / 2 / 0 | 39.46 | 15 | 89.57 |
| OpenCode 1.19.5 | 17 / 2 / 0 | 57.92 | 10 | 90.56 |

All three shared subjects omit account-usage and standalone-model-catalog
reads, so those two cases skip. Kimi also lacks `steer`, so its two steer
cases skip. These are explicit capability skips, not platform exclusions;
summary output names each missing capability and separates pass/skip/fail.
The vendor runner collects tests for all runtimes but only runs the selected
backend, so unrelated test files are reported skipped by Vitest.

The first Linux pass required no runtime, fixture, assertion or native
wait change. The macOS and Windows CI executions establish their native
behavior results; package availability alone is not proof they pass.
There is no platform exclusion or missing-binary success path in the new
matrix. Failed first attempts must remain in the evidence if a fixture
change or unchanged rerun is later necessary.

CI limits shared-case concurrency and Vitest workers to 2 on every platform,
so a cold runner does not start every native session at once. This changes
only test scheduling, not the adapter or its native waits.

Each new job has a 20-minute ceiling and each test step has a 12-minute
ceiling. They are CI execution limits, not modified test assertions or
runtime deadlines. Existing traces and logs upload on failure. Job and step
timestamps provide the follow-up durations; no external telemetry is added.
The separate [Windows Pi RPC investigation](windows-ci-2026-10-26.md)
means an alive runner timing out and a runner losing communication must be
reported separately. These limits do not prove that either failure is fixed.

[Run 40808334526](https://github.com/botiverse/oar/actions/runs/40808334526)
tested head `07e9068` before the Windows Pi RPC job split was rebased in.
All seven other ACP jobs passed. GitHub step/job timestamps, in seconds,
exclude runner queue time; job duration includes setup and artifact upload:

| Platform | Backend | Shared seconds | Vendor seconds | Job seconds | Result |

| Linux | Grok | 35 | 74 | 131 | pass |

| Windows | OpenCode | 89 | 430 | 580 | two vendor timeouts |

The first Windows failures are retained, not replaced by a later result:

- [Grok job](https://github.com/botiverse/oar/actions/runs/40808334526/job/123232487831):
  npm installation, version and readiness probes succeeded. Every session
  opening timed out at ACP `initialize` after the unchanged 15 seconds.
  Shared results were 1 pass, 2 capability skips and 16 failures; vendor
  tests did not run. The version's npm wrapper retains a Node bootstrap on
  Windows, while its npm postinstall replaces the Unix entry with a native
  binary link. This is a launch-path difference, not yet a causal finding.
- [OpenCode job](https://github.com/botiverse/oar/actions/runs/40808334526/job/123232487877):
  all 17 shared cases passed with 2 capability skips. Eight vendor cases
  passed; `serveMcpTools` and `tools/list_changed` reached their unchanged
  120-second test limits. The served-tool trace contains an accepted prompt
  and commands update but no tool call or turn end, so that failure is not
  merely teardown after a completed turn. A separate mixed stdio/HTTP MCP
  test did complete its tool calls and disposal. The cause remains open.

The follow-up keeps both Windows jobs required. Grok's
[startup comparison](grok-acp-startup.ts) sends the same raw `initialize`
request through OAR's resolved installation, the npm wrapper, its explicit
Node bootstrap, the installed native executable and native overlapped
pipes. Each uses fresh isolated configuration, synthetic credentials and
the same 15-second bound; no model is called. Outcomes and bounded redacted
stderr are saved as `grok-acp-startup.jsonl`. It records diagnostic outcomes
without replacing or relaxing the behavior gate. The request uses OAR's
client identity and file/terminal capabilities. On Linux all five paths
initialized: OAR installation 278 ms, npm wrapper 267 ms, Node bootstrap
1760 ms, native 284 ms and native overlapped 271 ms. These are single cold
samples, not a Windows conclusion.

Windows test processes also forward stderr for the OpenCode investigation.
`OAR_TEST_MCP_PROGRESS=1` writes the two MCP probes' current phase, provider
request count and, for the catalog probe, MCP method names every ten seconds.
It records no headers, credentials or model payloads and changes no waits.
No adapter fix, timeout
change, platform exclusion or allowed failure has been inferred from these
first failures.

## Deferred coverage

### OpenCode v2

The existing local scripted provider and shared behavior probe work on
2.2.0, with 15 passing cases and four capability skips in the October 28
inspection. The current vendor suite is v1-specific: five of its ten cases
failed on v2 2.0.30 because they assumed direct MCP tools in the provider's
`tools` array, classifications based on that array, or v1 prompt replacement.
See the [October 16 evidence](runtime-version-checks/2026-10-16.md).

A v2 CI job needs separate assertions at its actual provider/tool boundary,
then cold-start and disposal measurements on all three platforms. It must
use `@opencode/cli` in a separate installation because both version lines
provide the `opencode` command. Changing current assertions to make v2
look like v1, silently skipping their failures, or installing both global
commands in one job would lose coverage. No v2 CI job is added here.

### Antigravity

The [official ACP registry](https://raw.githubusercontent.com/agentclientprotocol/registry/main/antigravity-acp/agent.json)
currently lists 1.4.4 binaries for Linux, macOS and Windows, on x64 and
arm64. Linux uses `agy_acp_server.par --uid=`; Windows uses
`agy_acp_server.exe`. The fixture can use a local Gemini provider and
synthetic key without account authorization. The existing shared probe
passes 15 cases with four capability skips on Linux.

Its matching `localharness_external` companion must stay beside the server.
The Linux archive measured 321.24 MiB, and the extracted server/companion
files total 1012.48 MiB before the server's additional extraction cache.
Those [measured artifacts](antigravity-steering-2026-10-29.md) make a
version/platform/checksum-keyed extraction cache and cold-start timing
necessary before adding jobs. macOS and Windows fixture routing, companion
startup and cleanup remain unverified here. Registry distributions are
proprietary; the registry links the vendor terms. This PR records feasibility
only and does not substitute the interactive `agy` program or its private
language-server API for ACP.
