# Codex shared app-server evidence: 2026-10-29

Codex 0.165.0 has the native primitives needed for a Linux sharing candidate,
with two mandatory adapter rules: a live OAR session must exclusively own its
thread, and releasing it must cancel/unsubscribe and stop its native background
commands. This report does not enable sharing. macOS and Windows results are
still required before offering it on those platforms, and the future OAR pool
must prove its routing and exit records in adapter tests.

## Scope

Linux x64 on xxwork, Node 24.19.0, native Codex 0.165.0. Two root threads use
one app-server connection, different working directories, and different MCP
server configurations under the same server name. Model requests terminate at
a local scripted provider. `experimentalApi` and `multi_agent_v2` are enabled;
code mode is disabled so the fixture calls native tools directly. No archive,
real account, external model request, or OAR shared runtime is used.

[Probe](codex.ts), [fixture](codex-fixture.ts), [resources](codex-resources.ts),
and [selected values](selected-2026-10-29.json) are rerunnable. The source
inspection used Codex commit
[`360319d8`](https://github.com/openai/codex/blob/360319d8dee62d87e2d59fc0c21805d79519cfed/codex-rs/app-server/src/request_processors/thread_processor.rs).

## Native observations

| Gate | Observed on Linux |
| --- | --- |
| Concurrent roots and messages | Both roots finish concurrently; each answer has its own thread id and marker. |
| Working directory | Native `exec_command` prints the corresponding root's directory. |
| MCP isolation | Both roots define `scope.echo`, but each call reaches only its own server and marker. |
| Child attribution | `subAgentActivity` belongs to root A, names the child thread, and `thread/read` independently reports `parentThreadId = A`. The child makes a local model request and emits its own notifications. Root B is not that child. |
| Cancellation | Interrupt A's held turn; B remains active and completes when its own model response is released. |
| Scoped tool cleanup | Each root starts a command with a real child process. Terminating A's native process id with B's thread id returns false and leaves both trees alive. Terminating it with A's thread id stops A's parent and child; B's parent and child stay alive. |
| Loaded resume | Resuming the subscribed thread requesting `gpt-5.2` returns and actually sends `gpt-5.1`. A successful resume response does not mean the override applied. |
| Unsubscribe then resume | After unsubscribe the thread remains loaded. An idle, unsubscribed resume requesting `gpt-5.2` reloads it, and the next provider request uses `gpt-5.2`. |
| Close/resume race | Concurrent unsubscribe/resume both return; a subsequent resume and turn use the original thread id and complete. This is one ordering, not a proof of every possible interleaving. |
| Process failure | Kill the native app-server while two provider requests are held. The transport exits; subsequent reads for both roots reject; neither root receives a fabricated `turn/completed`. The future adapter must fan this exit out to every owned session. |

Tool cleanup uses `thread/backgroundTerminals/list` and `terminate` with
**native process ids**. OS PIDs and start identities are only independent
observations of whether the fixture's parent/child processes survived. They
are not the implementation of scoped cleanup. `thread/archive` is not used
because it would change persisted user state.

The inspected `ThreadProcessor` agrees with the experiment: configuration
changes on an already subscribed loaded thread are ignored with a warning;
an idle thread without a subscriber can be shut down and reloaded to apply
overrides. The current [app-server documentation](https://learn.chatgpt.com/docs/app-server)
also describes unsubscribe retention; the exact installed-version behavior
above comes from the probe and pinned source, not that evolving page.

## Resource comparison

Ten sessions, same executable, one short local-model turn per session. Order:
isolated, shared, shared, isolated. Stable post-turn RSS was about **1,987 MiB
in 20 processes** for isolated placement versus **244 to 245 MiB in two
processes** for shared placement. The extra process is the npm launcher.
Non-lower-bound idle CPU windows were **0.6 to 1.6% of one core** isolated and
**0 to 0.2%** shared. The selected JSON retains every interval, including two
isolated intervals with exiting helper processes that were excluded from the
CPU comparison. This supports lower RSS and no increased idle CPU in these
samples only; active workload CPU and long-term growth were not measured.

## Required Phase 2 behavior

1. Reject resume with a typed in-use reason if another still-open OAR session
   owns that thread in the pool. Do not silently keep its earlier configuration.
2. On disposal, finish per-thread cleanup and unsubscribe without archiving.
   Once idle and unowned, a later resume can reload the thread and apply options.
3. Check the model returned by resume, and refuse a mismatch. The experiment
   also checks the actual provider request to establish that the native reload
   applies the requested model.
4. Route known roots by their exact ids. Admit children only through native
   parent links; preserve unassociated notifications without inventing ancestry.
5. On a shared transport exit, end every still-owned OAR session with its own
   exit record. Native turn-completed notifications are not guaranteed.

These rules are integration work, not changes made by this evidence PR.
