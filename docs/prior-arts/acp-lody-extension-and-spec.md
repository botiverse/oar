# Part A: Lody's extension protocol (`acp-extension-core`)

## A.1 Shape of the contract

- Three placement rules, in order (`lody/packages/acp-extension-core/README.md:39-47`): use standard ACP when it fits; otherwise put Lody semantics under `_meta.lody.<feature>` on the standard message; add a `_lody/...` JSON-RPC method only when ACP has no equivalent.
- Negotiation (`README.md:89-98`, `src/capabilities.ts:1-72`):
  - Agent features: `InitializeResponse.agentCapabilities._meta.lody.<feature>` (`LodyExtensionCapabilities`, `src/capabilities.ts:58-72`).
  - Client features: `InitializeRequest.clientCapabilities._meta.lody.<feature>` (`LodyClientExtensionCapabilities`, `src/capabilities.ts:12-15`).
  - Every feature value is an object with at least `{ "version": 1 }` (`LodyVersionOneCapability`, `src/capabilities.ts:1-3`). A missing key means unsupported; one feature never implies another. Features needing both directions (only `subagentEvents` today) are active only when both peers advertise them.
  - Not negotiated through ACP's own `agentCapabilities` fields; it is purely `_meta`.
- Method names: all custom methods are `_lody/...` (`src/methods.ts:3-15`). `normalizeLodyExtensionMethod` re-adds a missing leading underscore (`src/methods.ts:70-72`), and the CLI strips it before matching (`lody/apps/cli/src/agent/agent-client.ts:1522`), so the Lody client tolerates both `_lody/x` and `lody/x` on the wire.
- Typed request/notification maps bind each method to its DTO: `LodyExtensionRequestMap` (`src/methods.ts:20-49`), `LodyExtensionNotificationMap` (`src/methods.ts:51-56`), `LodyExtensionRequestHandlers` for providers (`src/methods.ts:62-68`).
- Field naming rules: absolute timestamps are epoch seconds with `EpochSeconds` in the name; `durationMs` is milliseconds (`README.md:195`). Adapters emit only current contracts; legacy compatibility lives at the consumer and should be time bounded (`README.md:204`).

## A.3 Related non-Core conventions seen in the same code

- Claude adapter also serves a pre-Lody steering contract: request `_session/steering` (`lody/packages/acp-extension-claude/src/acp-agent.ts:661`) advertised as top-level `InitializeResponse._meta.steering.supported: true` (`acp-agent.ts:2682-2708`), with results `startedNewTurn` / `promptRequired` (`acp-agent.ts:685-691`). The comment calls it "the existing ACP steering extension contract", but it does not appear anywhere in the upstream ACP repo (grep in Part B).
- Lody CLI still parses legacy steering caps `agentCapabilities._meta.codex.steer` and `_meta.claudeCode.steer` (`acknowledged-steer.ts:60-89`) and legacy notifications `_acp_ext:session_usage_update`, `_acp_ext:session_rate_limits`, `_acp_ext:codex_proposed_plan`, `_claude/taskLifecycle`, `_kimi/taskLifecycle`, plus `_meta["lody.ai/kimi"]` (`lody-acp-extension.ts:155-161,183-203,265-284`).
- JetBrains AIR capabilities under `_meta["jetbrains.air"]` (`lody/packages/acp-extension-claude/src/air-extension.ts:1-27`) and Devin's `cognition.ai/subagent_context` (`agent-client.ts:911-934`) show the ecosystem uses vendor-keyed `_meta` freely.

## A.4 Publication, versioning, fallback

- Published on npm as **`acp-extension-core`**: versions 0.0.1 through 0.1.9, `latest` = 0.1.9, registry `time.modified` 2026-09-27 (`npm view`). I diffed the npm 0.1.9 tarball's `src/` against the repo: identical. It is a 0.x package, so no semver stability promise. Runtime dependency: `@agentclientprotocol/sdk ^1.4.0` (`package.json`). MIT license.
- Inside the Lody monorepo it is forced to `workspace:*` (`lody/pnpm-workspace.yaml`, `overrides`), while each adapter pins `"acp-extension-core": "0.1.9"` (e.g. `lody/packages/acp-extension-codex/package.json:77`).
- There is **no package-level protocol version field** and no `_lody` version handshake. Versioning is per feature: each capability object carries `version: 1` (literal type), and some payloads repeat it (`LodySubagentEvent.version`, `LodyTaskMeta.version`, `LodyActivityMeta.version`, `goalControl.version`, `forkAtTurn.version`, `worktreeProject.version`, `LodyElicitationMeta.version`). The specs that define the newer pieces are all `Status: draft` (`lody/specs/subagent-events.md:3`, `session-goal-control.md:3`, `acp-session-titles.md:3`, `usage-delivery.md:3`).
- Client fallback when an agent does not advertise:
  - No or malformed `_meta.lody`: capability set becomes `{}` and every feature is off (`lody-acp-extension.ts:180-182`).
  - `steering` absent (or capability info unavailable/provisional): the composer's Guide/Steer action appends to Lody's regular queue instead; no steer request is sent (`lody/specs/session-history-writes.md:79-85`); `steerPrompt` throws if called (`agent-client.ts:2438-2441`).
  - `subagentEvents` absent: provider's existing path (tool calls with `_meta.lody.task`, or legacy `_claude/taskLifecycle`) (`lody/specs/subagent-events.md:25-30`); stray events are dropped (`agent-client.ts:1539`).
  - `goal` with neither `controlActions` nor `promptActions`: `/goal ...` slash text as an ordinary prompt (`goal-control.ts:46-49`, `agent-client.ts:1457-1458`); action not in `actions`: unavailable.
  - `sessionTitle` absent: Lody runs its isolated title generator; untagged titles trusted only for legacy Claude/Grok (`lody/specs/acp-session-titles.md`; `agent-client.ts:1702-1723`).
  - `rateLimits.query`, `subagents.cancel`, `forkAtTurn` absent: typed errors `ACP_RATE_LIMITS_UNSUPPORTED`, `ACP_SUBAGENT_UNSUPPORTED`, `ACP_FORK_AT_TURN_UNSUPPORTED` (`agent-client.ts:1364-1366,1379-1381,2082`).
  - `usage` absent: nothing changes; `_lody/session/usage_update` is parsed regardless, and the standard `usage_update` still feeds the context meter.
  - `sessionHistory` absent: falls back to `session/load` (requires `loadSession`) (`history-session-catalog-client.ts:317-329`).

# Part B: upstream ACP

## B.1 Protocol version and method surface

- **Current stable protocol version is 1.** `ProtocolVersion::LATEST = V1`; `V2` is "an unstable draft", only behind feature `unstable_protocol_v2` (`agent-client-protocol/agent-client-protocol-schema/src/version.rs:20-39`). TS SDK: `PROTOCOL_VERSION = 1` (`acp-typescript-sdk/src/schema/index.ts:323`; also 1 in npm 1.7.0).
- Stable v1 methods (`agent-client-protocol/schema/v1/meta.json`):
  - Agent side: `initialize`, `authenticate`, `session/new`, `session/load`, `session/set_mode`, `session/set_config_option`, `session/prompt`, `session/cancel` (notification), `session/list`, `session/delete`, `session/resume`, `session/close`, `logout`.
  - Client side: `session/request_permission`, `session/update` (notification), `fs/read_text_file`, `fs/write_text_file`, `terminal/create`, `terminal/output`, `terminal/release`, `terminal/wait_for_exit`, `terminal/kill`, `elicitation/create`, `elicitation/complete`.
  - Protocol: `$/cancel_request`.
- Unstable v1 additions (`schema/v1/meta.unstable.json`): agent `providers/list|set|disable`, **`session/fork`**, `mcp/message`, `nes/*`, `document/did*`; client `mcp/message`.
- `session/set_model`: **removed**. "The never-stabilized `session/set_model` API and related session model response fields have been removed from the protocol artifacts. Agents should continue to expose model selection through Session Config Options" (`docs/rfds/updates.mdx:264`). Neither v1 schema contains it.
- Stable v1 `SessionUpdate` variants (`schema/v1/schema.json`): `user_message_chunk`, `agent_message_chunk`, `agent_thought_chunk`, `tool_call`, `tool_call_update`, `plan`, `available_commands_update`, `current_mode_update`, `config_option_update`, `session_info_update`, `usage_update`. Unstable v1 adds `plan_update`, `plan_removed`, `notice`, `compaction_update`, `compaction_summary_chunk`, `subagent_update`, `session_message`, `session_message_chunk` (`schema/v1/schema.unstable.json`). The v1 union is **closed** (no catch-all); v2 adds an `other` variant.
- Stabilization history (`agent-client-protocol/CHANGELOG.md`): session/list + `session_info_update` (`:378`), session/resume and session/close (`:294-295`), `usage_update` (`:205`), session/delete (`:206`), elicitation (`:64`), `$/cancel_request` (`:134`), tool call `name` (`:50`).
- Stable capability fields: `AgentCapabilities {loadSession, promptCapabilities, mcpCapabilities, sessionCapabilities {list, delete, additionalDirectories, resume, close}, auth}`; `ClientCapabilities {fs, terminal, session, auth, elicitation}`. Unstable adds `sessionCapabilities.fork`, `clientCapabilities.subagents`, `clientCapabilities.plan`, `providers`, `nes`.
- v2 draft method surface (`schema/v2/meta.json`): agent `initialize`, `auth/login`, `auth/logout`, `session/new`, `session/set_config_option`, `session/prompt`, `session/cancel`, `session/list`, `session/delete`, `session/resume`, `session/close`; client only `session/request_permission`, `session/update`, `elicitation/create`, `elicitation/complete`. (No `session/load`, `session/set_mode`, `fs/*`, `terminal/*`.)
- RFD lifecycle stages (`docs/rfds/about.mdx:25-60`): Draft (championed, may be experimentally implemented behind a feature flag) -> Active (maintainer focus, not a stability commitment) -> Preview (fully implemented, broad review) -> Completed (only stage that can be a one-way door). Stage of each RFD is its group in `docs/docs.json:188-234`.

## B.2 RFDs by topic

### Message queueing / steering a running turn

- **No RFD exists for queueing or steering.** Grep of `docs/` and `schema/` for steer/queue finds only statements that it is out of scope:
  - `docs/rfds/v2/prompt.mdx:88`: "This RFD does not specify queueing, steering, or whether agents insert new prompts while busy."; `:336`: "Queueing, steering, sender identity, safe retries, and idempotency guarantees remain outside this change."
  - `docs/rfds/v2/overview.mdx:117` (2026-07-20 revision): "steering and queueing remain separate concerns."
  - `docs/rfds/subagents.mdx:47-50,1126-1132`: subagent sessions must not imply clients can call "future queueing and steering methods".
- Closest groundwork: **"v2 Prompt Lifecycle"**, status **Active (v2)**, `docs/rfds/v2/prompt.mdx`. In v2, `session/prompt` returns as soon as the user message is **inserted** into the conversation, with an agent-generated `messageId` (`:41-61`); turn progress moves to `session/update` `state_update` (`running` / `idle` with `stopReason` / `requires_action`) (`:200-253`); failures after insertion become `idle` with `stopReason:"error"` plus a JSON-RPC error object (`:255-306`). Receiving or queueing input is explicitly not acceptance (`protocol/v2/prompt-lifecycle.mdx:144`). The RFD notes a future queue design might need an earlier receipt, separate from this (`:379-381`). The v1 prompt is unchanged.

### Subagents / nested sessions

- **"Subagent Sessions"**, status **Draft** (schema already shipped as unstable in Rust crate 1.10.0, `CHANGELOG.md`), `docs/rfds/subagents.mdx`. Each exposed subagent is its own ACP session. v1 negotiation: client-only `clientCapabilities.subagents: {}`; no agent capability; agent must not send these updates otherwise (`:56-81`). The parent session sends `session/update` `subagent_update { sessionId (child), title?, description?, capabilities? { cancel? }, state?, _meta? }` (nullable patch semantics) before any traffic bearing the child's ID; the outer `sessionId` is the immediate parent, supporting arbitrary nesting (`:83-170`). Child events then flow automatically under the child's `sessionId`; clients must not `session/load`/`resume` a child (`:204-247`). Inter-session messages use new `session_message` / `session_message_chunk` updates with `messageId`, `senderSessionId?`, `recipientSessionId?` (`:249-300`). No lifecycle enum: the child's work state is a `StateUpdate` snapshot (`running`/`idle`+stopReason/`requires_action`/`unknown`) mirrored on `subagent_update.state` (`:464-480`). Cancel via ordinary `session/cancel` on the child ID only if `capabilities.cancel` is advertised (`:771-800`). Cost: no inferred aggregation, parent and child costs may overlap, never sum them (`:843-873`). **There is no field linking a child to the parent's spawning tool call** (FAQ `:1116-1124` explains a subagent is deliberately not modeled as a tool call). Prompting or steering a subagent is explicitly not allowed (`:1126-1132`).

### Usage / cost

- **"Session Context Size and Cost"**, status **Completed** (stabilized), `docs/rfds/session-usage.mdx`. `session/update` `usage_update { used, size, cost?: { amount, currency (ISO 4217) } | null }`: context tokens in use, context window size, and **cumulative session** cost. Sent after session setup/restore and whenever it changes; no per-turn tokens (`:39-116`).
- **"End-Turn Token Usage"**, status **Draft**, `docs/rfds/end-turn-token-usage.mdx`. Strawman: optional `usage { totalTokens, inputTokens, outputTokens, thoughtTokens?, cachedReadTokens?, cachedWriteTokens? }` on the turn-completion signal (v1 `PromptResponse`, v2 idle `state_update`) (`:31-40,82-93`). Open questions include per-turn vs cumulative and cost separation (`:95-102`). Already present as unstable `PromptResponse.usage` in `schema/v1/schema.unstable.json`. Nothing covers per-model breakdown, deltas, or accounting scopes/segments.

### `_meta` conventions and extensibility rules

- Normative v1 rules, `docs/protocol/v1/extensibility.mdx`:
  - `_meta` is `{ [key: string]: unknown }` on types that define it (`:8-14`). Root keys `traceparent`, `tracestate`, `baggage` SHOULD be reserved for W3C trace context (`:37-41`). **Implementations MUST NOT add custom fields at the root of a spec type** (`:43`).
  - **Custom methods: any method name starting with `_` is reserved for extensions** (`:45-47`); custom requests (`:54-67`) and notifications (`:99-111`). Unknown custom request -> respond `-32601 Method not found` (`:84-95`); unknown notifications SHOULD be ignored (`:113`).
  - Extensions SHOULD advertise via `_meta` inside capability objects, e.g. `agentCapabilities._meta["zed.dev"] = {...}` (`:115-138`). The example uses a domain key; no namespace format is mandated.
- **"Meta Propagation"**, status **Completed**, `docs/rfds/meta-propagation.mdx`: documents `params._meta` for client to agent propagation and reserves the three trace keys (`:10,41-45`).
- **"Enum Variant Extension"**, status **Active (v2)**, `docs/rfds/v2/enum-variant-extension.mdx`: in v2, enum and tagged-union values starting with `_` are for implementation extensions, non-underscore values are reserved for ACP, unknown values should be preserved and degraded gracefully (`:11,33-40`). v1 enums stay closed, and the TS SDK client validates `session/update` against a closed Zod union (`acp-typescript-sdk/src/acp.ts:1390-1394`), so inventing a new `sessionUpdate` kind in v1 breaks stock clients.

### `session/load` replay semantics

- v1 (stable), `docs/protocol/v1/session-setup.mdx`: `session/load` requires `loadSession` capability; the agent **MUST replay the entire conversation as `session/update` notifications** and respond only after all entries are streamed (`:106-188`, especially `:134`, `:176-178`). `session/resume` (capability `sessionCapabilities.resume`) **MUST NOT replay** history (`:190-243`).
- **"Session Resume"**, status **Completed**, `docs/rfds/session-resume.mdx`: resume like load but without returning previous messages.
- **"v2 Session Resume Replay"**, status **Active (v2)**, `docs/rfds/v2/session-resume-replay.mdx`: v2 removes `session/load`; `session/resume` gains optional `replayFrom` (`{ "type": "start" }` replays all retained history before responding; omitted = no replay); cursors are inclusive; agents need not retain every message, but retained user messages keep the `messageId` returned at insertion.
- **"Required Session Methods"**, status **Active (v2)**, `docs/rfds/v2/required-session-methods.mdx`: advertising `capabilities.session` in v2 means `session/list`, `session/resume`, `session/close` are mandatory; `session.fork` stays optional/unstable.

### Permission requests

- v1 (stable), `docs/protocol/v1/tool-calls.mdx:213-231`: `PermissionOption { optionId, name, kind, _meta? }` with `kind` in `allow_once`, `allow_always`, `reject_once`, `reject_always` (closed enum in `schema/v1/schema.json`). Outcome is `cancelled` or `selected { optionId }`; on `session/cancel` the client MUST answer all pending permission requests with `cancelled` (`tool-calls.mdx:193-210`, `prompt-turn.mdx:350`).
- **"v2 Permission Requests"**, status **Active (v2)**, `docs/rfds/v2/permission-requests.mdx`: every request gets required `title`, optional `description`, and optional tagged `subject` (`tool_call { toolCall: {toolCallId} }` or `command { command, cwd, toolCallId?, terminalId? }`); unknown subjects preserved. v2 schema opens `PermissionOptionKind` with `other`.

### Terminals

- v1 (stable), `docs/protocol/v1/terminals.mdx`: client-executed terminals gated by `clientCapabilities.terminal: true` (`:8-20`); methods `terminal/create|output|release|wait_for_exit|kill`; tool-call content `{ type: "terminal", terminalId }`.
- **"v2 Client Filesystem and Terminal Capabilities"**, status **Active (v2)**, `docs/rfds/v2/client-filesystem-terminal-capabilities.mdx`: v2 removes `clientCapabilities.fs`/`terminal`, all `fs/*` and `terminal/*` client methods, and client-owned terminal content ("not widely adopted"; agents move to their own sandboxing).
- **"v2 Terminal Output"**, status **Active (v2)**, `docs/rfds/v2/terminal-output.mdx`: agent-owned display-only terminals; tool call content `{type:"terminal", terminalId}` as an anchor; `terminal_update` upsert `{ terminalId, command?, cwd?, output? {data: base64}, exitStatus? }` plus `terminal_output_chunk`; the client gets no control over the process.

### MCP servers in `session/new`

- v1 (stable), `docs/protocol/v1/session-setup.mdx:369-381,520-530`: `mcpServers` is a required array on `session/new` and `session/load` (optional on resume/fork per schema). **All agents MUST support stdio**; HTTP and SSE are optional, gated by `agentCapabilities.mcpCapabilities.http` / `.sse`.
- **"MCP over ACP"**, status **Draft** (unstable schema, made request-scoped in crate 1.10.0), `docs/rfds/mcp-over-acp.mdx`: client or proxy declares an MCP server with `"type": "acp"` and MCP requests travel over the ACP connection as `mcp/message` keyed by `serverId` and a caller `requestId`; targets MCP 2026-07-28 only, no MCP init handshake.

### Other RFDs relevant to a bridge

- **"Session Fork"**, **Draft** (unstable `session/fork`, capability `sessionCapabilities.fork: {}`), `docs/rfds/session-fork.mdx:36-48`. Forking at a specific message is mentioned only as future work, so Lody's `forkAtTurn` has no upstream equivalent yet.
- **"Session Close"** Completed; **"Session List"** Completed; **"Session Info Update"** Completed (`session_info_update { title?, updatedAt?, _meta? }`); **"Message ID"** Completed (optional agent-owned `messageId` on message chunks); **"Request Cancellation"** Completed (`$/cancel_request`).
- **"Session Notices"**, **Preview**, `docs/rfds/session-notices.mdx`: fire-and-forget `notice` update; v1 gated by `clientCapabilities.session.notices`; not replayed (`:69`).
- **"Session Compaction"**, **Preview**, `docs/rfds/session-compaction.mdx`: `compaction_update` and `compaction_summary_chunk`.
- **"Streamable HTTP & WebSocket Transport"**, **Active**, `docs/rfds/streamable-http-websocket-transport.mdx`: single `/acp` endpoint; HTTP POST + long-lived SSE GET streams (connection and per session), or WebSocket upgrade; same JSON-RPC as stdio.
- **"Proxy Chains"**, **Draft**, `docs/rfds/proxy-chains.mdx`.

## B.3 TypeScript SDK agent side (local `@agentclientprotocol/sdk@1.4.0`)

- Two APIs coexist since 0.27.0 (`acp-typescript-sdk/MIGRATION_0.26_0.27.md:1-38`):
  - **Current: app builder.** `acp.agent({ name })` (`src/acp.ts:1829-1831`) returns `AgentApp` (`src/acp.ts:1841-2073`): `.onRequest(method, handler)`, `.onNotification(method, handler)`, `.onConnect(handler)`, `.connect(stream | clientApp)` returning `AgentConnection { client: AgentContext, signal, closed, close() }` (`src/acp.ts:191-219`), and `.connectWith(stream, op)`. Handlers get `ctx = { params, signal, client: AgentContext, requestId }` (`src/acp.ts:958-989`). Method name constants: `acp.methods.agent.*` / `acp.methods.client.*` (`src/acp.ts:118-180`). Example: `src/examples/agent.ts:281-295`.
  - **Deprecated: `AgentSideConnection`** (`src/acp.ts:2675-2944`), constructed as `new AgentSideConnection((conn) => agentImpl, stream)` (`:2692-2696`) where the impl implements interface `Agent` (`src/acp.ts:3890-4252`: required `initialize`, `newSession`, `authenticate`, `prompt`, `cancel`; optional `loadSession`, `unstable_forkSession`, `listSessions`, `deleteSession`, `resumeSession`, `closeSession`, `setSessionMode`, `setSessionConfigOption`, `logout`, provider/NES/document methods, `extMethod`, `extNotification` at `:4236,4248`). Internally it is adapted onto `AgentApp` by `legacyAgentApp` (`src/acp.ts:2374-2556`). Outbound helpers: `sessionUpdate`, `requestPermission`, `readTextFile`, `writeTextFile`, `createTerminal`, `createElicitation`, `request`, `notify`, deprecated `extMethod`/`extNotification` (`:2711-2892`). Still present in npm 1.7.0.
- Extension methods and notifications:
  - App API: register a custom inbound method by passing a params parser (a Zod schema or function) as the second argument: `.onRequest("_oar/x", { parse }, handler)` / `.onNotification("_oar/y", parser, handler)` (`src/acp.ts:1917-1999`). Without a parser an unknown method name throws at registration (`:1946-1951`). Outbound custom calls: `ctx.client.request<Resp>("_oar/x", params)` and `ctx.client.notify("_oar/y", params)` (`AgentContext.request/notify`, `src/acp.ts:283-333`). Lody's Claude adapter uses exactly this for `_lody/session/steer` (`lody/packages/acp-extension-claude/src/acp-agent.ts:11028-11050`).
  - Legacy API: `extMethod(method, params)` / `extNotification(method, params)` receive any request/notification that is not a built-in method, with the **full method name including the leading `_`** (`src/acp.ts:2514-2553`).
  - Unhandled inbound requests get `-32601 Method not found`; unhandled notifications are dropped silently (`src/jsonrpc.ts:1409-1415`).
  - Inbound `session/update` on the client side is validated with a closed Zod union (`src/acp.ts:1390-1394`, `src/schema/zod.gen.ts:2805`), which is why new data must ride in `_meta` or `_` methods in v1.
- Transports:
  - **stdio**: `acp.ndJsonStream(output: WritableStream<Uint8Array>, input: ReadableStream<Uint8Array>)` (`src/acp.ts:48-53`, implementation `src/stream.ts:40`); typically `Writable.toWeb(process.stdout)` and `Readable.toWeb(process.stdin)` (`src/examples/agent.ts:281-284`).
  - **Any custom transport**: anything shaped `Stream = { writable: WritableStream<AnyMessage>, readable: ReadableStream<AnyMessage> }` (`src/acp.ts:34-39`, `src/stream.ts:13-28`) can be passed to `AgentApp.connect`. In-process: `agentApp.connect(clientApp)` uses a memory stream pair (`src/acp.ts:2046-2063`).
  - **Streamable HTTP + WebSocket server** (experimental export `@agentclientprotocol/sdk/experimental/server`): `new AcpServer({ agent | createAgent | createLegacyAgent })` (`src/server.ts:37-116`), with Node adapters `createNodeHttpHandler(acpServer)` and `createNodeWebSocketUpgradeHandler(acpServer, wss)` from `experimental/node` (`src/node-adapter.ts:29,42`). Example: `src/examples/http-server.ts:100-150`. Client-side counterparts: `experimental/http-client` (`createHttpStream`, `src/http-stream.ts:57`) and `experimental/ws-client` (`createWebSocketStream`, `src/ws-stream.ts:66`).
  - **Dual v1/v2**: `agentProtocolRouter().withV1(a).withV2(b).connect(stream)` picks the version from `initialize` (`src/protocol-router.ts:38-60,308`; example `src/examples/dual-version-agent.ts:147`); the v2 app API is under `@agentclientprotocol/sdk/experimental/v2` (`src/v2/acp.ts:2950-2964`).
