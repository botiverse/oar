# Codex ACP adapters: feature inventory

Research date 2026-10-06, for the design of `oar acp codex` (codex app-server exposed as an ACP agent).

## Sources and versions

- Zed codex-acp: `zed-industries/codex-acp` at `296069e` (2026-07-22). Crate version 0.16.0 (`Cargo.toml:3`). All codex crates pinned to git tag `rust-v0.137.0` (`Cargo.toml:22-36`, codex-core at `:27`). ACP Rust crate `agent-client-protocol =0.14.0` with feature `unstable` (`Cargo.toml:21`). `README.md:4-6` states that development moved to `agentclientprotocol/codex-acp`, "built on the new Codex App Server". This clone is the frozen in-process variant.
- Lody: monorepo `lodyai/lody` at `86e0da5` (2026-10-06). Submodule `packages/acp-extension-codex` at `51a07ee` (2026-09-30), package 1.12.0, depends on `@openai/codex ^0.159.2` (lock resolves 0.159.2, `package-lock.json:926-927`), `@agentclientprotocol/sdk ~1.5.0`, `acp-extension-core 0.1.9` (`package.json:75-77`). Submodule `packages/acp-extension-core` at `85ec3ab` (2026-10-01). `readme-dev.md:192-198`: the adapter is a fork that merged upstream `agentclientprotocol/codex-acp` main at `ba7b216` on 2026-09-30. So Lody is the upstream app-server adapter plus a `_lody` layer.
- ACP spec: `agentclientprotocol/agent-client-protocol` at `216c364`. In v1, `session/fork` exists only in the unstable surface (`schema/v1/meta.unstable.json:18`, absent from `schema/v1/meta.json`). `usage_update` carries `used`, `size`, optional `cost`.

Path prefixes used below: `Z:` = `zed-industries/codex-acp/`, `L:` = `lodyai/lody/packages/acp-extension-codex/`, `C:` = `lodyai/lody/packages/acp-extension-core/`. Line numbers are at the shas above.

## 4. Differences that matter for `oar acp codex`

1. Integration point. Zed links codex-core 0.137 in process; Lody (forked from upstream `agentclientprotocol/codex-acp`) drives `codex app-server` 0.159.2 over JSON-RPC, which is exactly the OAR shape. Zed's own README points to the app-server adapter as its successor. Treat Lody/upstream as the reference implementation; use Zed only for mapping ideas (approval option labels, diff and terminal rendering).
2. Policy placement. Zed sets approval and sandbox at thread level via `Op::ThreadSettings` and otherwise inherits the user's codex config. Lody sends `approvalPolicy`, `approvalsReviewer`, `sandboxPolicy`, `model`, `effort`, `serviceTier` on every `turn/start`, defaults to workspace-write `agent` mode, and force-trusts session roots. Lody also adds an auto-review mode.
3. Concurrent prompts. Zed has no gate and relies on core injecting input. Lody v1 rejects with a pointer to `_lody/session/steer` (`turn/steer` plus `steer_applied` ack and `-32600` for proven non-delivery); Lody v2 queues. ACP has no standard steer, so OAR has to pick one of these.
4. Subagents. Zed drops all collab events. Lody routes child threads as draft ACP subagent sessions, or `_lody/subagents/event`, or plain tool calls.
5. Session lifecycle. Lody has fork (`thread/fork`, with turn cutoff), delete (`thread/archive`), paginated history replay from app-server. Zed replays from rollout files and has no fork/delete.
6. Usage. Zed: only `usage_update`. Lody: `usage_update`, PromptResponse `usage`, per-turn accounting, rate-limit push and query. Neither sends `cost`.
7. Auth. Lody: API key (env or `_meta`), browser ChatGPT, device code via URL elicitation, custom gateway. Zed: browser login server and env API keys only.
8. Common gaps. Neither routes file reads/writes or shell through ACP `fs/*` or `terminal/*`; both execute inside codex and use the Zed `_meta.terminal_*` display convention. Neither emits `current_mode_update` or stop reasons other than `end_turn`/`cancelled`. Neither supports SSE MCP or audio input.
9. Slash commands. Zed: `/review*`, `/init`, `/compact`, `/logout`. Lody: `/review*`, `/compact`, `/goal`, `/plan`, `/status`, `/mcp`, `/skills`, `/rename`, `/logout`, and `$skill` commands; no `/init`.
10. Lody doc drift: README:18 promises `_meta.lody.task` on legacy subagent tool calls, but the live code no longer emits it.
